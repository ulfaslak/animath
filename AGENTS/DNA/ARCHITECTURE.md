# Architecture

## Shape

A pnpm workspace with three packages and one rule about the arrows between them:

```
packages/engine   ← pure game rules. Imports nothing.
      ▲      ▲
      │      │
packages/client   packages/server
(Vite, Three.js,  (Hono, ws, Drizzle,
 Svelte overlay)   Postgres)
```

The engine knows the rules of the game and nothing about screens, sockets or databases. The client renders and collects input. The server persists and, later, arbitrates. Client and server may both import the engine; neither imports the other, and the engine imports neither. Anything that decides an outcome — damage, a catch, an answer's correctness, whether a tile is walkable — is engine code.

To see the current tree:

```bash
tree packages -I 'node_modules|dist' --dirsfirst
```

### The authority seam (how multiplayer slots in)

```
   UI / renderer            Authority                 engine
 ┌──────────────┐  intent  ┌──────────────┐  calls  ┌──────────┐
 │ keyboard,    │ ───────▶ │ validate,    │ ──────▶ │ rules,   │
 │ Svelte panel │          │ apply, emit  │ ◀────── │ formulas │
 │ Three scene  │ ◀─────── │              │         └──────────┘
 └──────────────┘  event   └──────────────┘
```

`Authority` (`protocol.ts`) is `dispatch(intent)` + `subscribe(listener)`. The client has exactly one authority instance and everything above it is a consumer of events.

- **Today**: `packages/client/src/authority/local.ts` — `LocalAuthority` runs the engine in-process. Its own randomness (the encounter roll after each step, a battle's seed, a doctor visit's seed) is keyed by the world seed and its count of completed steps (and of visits), never by `Math.random`; see [[INVARIANTS]] § Authority. After a battle it emits `party-changed` (the whole party, HP written back, a caught animal added), or after a lost one `taken-to-doctor` (see § Modes); after each heal at the doctor, `party-changed` again. A `party` intent goes to `applyPartyIntent` with what the player is doing (`battle` while one is in progress, `doctor` during a visit, else `explore`) and, while a game is under way, is always answered with `party-edited`: facts only. The party it starts with passes through `normalizeNickname`, as a rename does. The whole game fits in a `SavedGame`: `snapshot()` takes one at any moment, a battle in progress included (its state, never its seed, which is derived again from the step count), and `start({ game })` picks one up, emitting `welcome` and then, for a saved battle, `battle-started`. A doctor visit is not part of it: a reload closes the visit, keeping what it healed. The client saves the game (§ Saving); a server authority would keep it itself.
- **The title**: until a game is under way (at load, and after `leave-game`) the authority takes one intent, `new-game { speciesId, nickname? }`: the engine's `chooseStarter` checks it, the starter gets a minted id, and the answer is `welcome` with `newGame: true` (a game picked up has `newGame: false`), or `new-game-refused { reason }`. Mid-game it is refused (`game-in-progress`). `leave-game` (Quit to title) is accepted only while exploring (in a battle or at the doctor it does nothing), answers `game-left` and stops the game where it stands: `snapshot()` still holds it. Continue is the host's call, `start({ game })` with the autosave's `resumable()`, because the save is the client's; a server authority would take a `continue` intent there.
- **Words**: events carry what happened, and the client chooses the words for its own screens — the battle narration, everything the doctor says, the line after a lost battle, who goes first after a party edit (from `party-edited`), the hint for Enter away from a tent (from `nothing-to-interact`, which carries no words). The authority's own line, a battle's closing line, is a `message` event carrying a `Line` from the engine's `LINES`: a copy key and the wild animal by id, never a sentence ([[DECISIONS]] § Copy and languages).
- **Multiplayer**: a `RemoteAuthority` with the same interface forwards intents over a WebSocket and relays the server's events. The server runs the engine against the shared world and is the source of truth. Nothing in the renderer, input or UI changes.

Two things keep that swap cheap: intents carry only what the player *chose* (a direction, an attack index, an answer string), never a computed outcome; and events describe what *happened* in enough detail to render without re-running the rules.

### Copy

```
 src/copy/en.yaml ┐  yaml() at build time          ┌ language.current ($state)
 src/copy/da.yaml ┴─────────────▶ plain objects ───┤ t('key', params) ─▶ Svelte markup
                                                   └ language.onChange ─▶ code outside Svelte

 engine event ─▶ Line { key, params: numbers, animals, attacks } ─▶ words(line) at draw time
```

- **Where the words live.** Every player-facing line is in `src/copy/<code>.yaml`, nested by screen (`battle.*`, `doctor.*`, `pause.*`, `explore.*`, …), and every species under its engine id: six forms (`name`, `a`, `the`, `wild`, `aWild`, `theWild` — "en vild ræv", "et vildt egern") and its attacks' names. Only the client reads the files. Both languages ship in the main bundle.
- **Loading.** `yaml()` in `vite.config.ts` parses a file when Vite builds, serves or tests it; the bundle holds its data and no YAML parser. A syntax error or a repeated key fails the build.
- **The language on screen.** `language.current` starts from `?lang=` (for that visit only), else the choice remembered on this device (`localStorage['animath.language']`), else the first of `navigator.languages` the game speaks (`da-DK` counts as `da`), else English. The pause menu's Language row calls `language.set()`, which switches, remembers (storage failures are ignored), sets `<html lang>` and calls the `onChange` listeners.
- **`t()` and lines.** `t()` reads `language.current` on every call, so Svelte markup that calls it re-renders the moment the language changes. What the screen says is kept as data until drawn — a `Line` (`lines.ts`: a key, and numbers, animals and attacks by id) for the battle narration and the message line, a `DoctorLine` for the doctor — and `words(line)` words it in the markup. A sentence stored as a string would stay in the language it was made in. Code outside Svelte (the Three.js layer, if it ever draws words) calls `t()` when it draws and redraws on `language.onChange`.
- **Names.** `names.ts` is the one place that turns an animal or an attack into words: a nickname is shown as stored and stands for every form; otherwise the species' forms come from the copy files. A sentence picks the form it needs (`{animal.theWild}`), and a form that starts a sentence gets a capital letter; a nickname is never changed.
- **Gaps.** A key missing from Danish shows in English; a key missing from English shows as the key. In development each gap logs one `console.warn`, which makes `scripts/screenshot.mjs` exit non-zero; production is silent. `copy-files.test.ts` fails on both.
- **Dev server.** An edited copy file swaps the words in place: `language.svelte.ts` accepts the hot update of `languages.ts`, so the game on screen and the `language` store survive it.
- **The engine emits no words** ([[DECISIONS]] § Copy and languages). Species and attacks are ids; events say what happened; refusals are codes (`BattleRejection`, `DoctorRejection`, `PartyRejection`); a `message` is a `Line` from `LINES`, typed so no string can ride along. Puzzle prompts are maths notation (`7 × 8 = ?`) and need no words. `no-words.test.ts` and the sweeps' `wordedStrings` check keep it so.

### Pointer input

```
 tap on a button (taps.ts)  ─▶ press(key) ─▶ KeyboardEvent on window ─▶ main.ts ─▶ the screen that is up ─▶ its key handler
 number pad finger down     ─▶ press(key)                                          (explore: keyboard.keydown)
 D-pad finger down / up     ─▶ hold / release of an arrow key
```

- **One path.** A click or a tap never reaches the authority, a view or a controller by a way of its own: the overlay's buttons send key presses (`input/press.ts`), which `main.ts` routes to the screen that is up exactly as a keyboard's (explore's `Keyboard` included, through `keydown`). So every guard a screen keeps on its keys (auto-repeat, busy, the quiet moment before a new choice takes a pick) holds for taps, and what a press means is the screen's key handler's to say, in one place. Components stay readers of their views, as before; a press is not a dispatch.
- **A tap** (`input/taps.ts`) is a pointer that goes down on a button (`data-press` names its key) and comes up on the same button, or hardly moved, on the same screen (`main.ts` counts every change of what takes keys, one animal's options in the pause menu apart from another's), followed by its `pointerId` so each finger is on its own; the key is pressed as it lifts, if the button still names it. The browser's `click` is not used for a pointer: it comes only once every finger has lifted (Talk and Menu under a thumb on the D-pad would never press), and it lands on whatever is under a finger lifted after the screen changed (the battle row under a thumb held on the D-pad into a battle). A click without a pointer (`detail` 0, a screen reader) still presses. The number pad presses as the finger lands, and the D-pad holds and lets go by its own pointer.
- **The pointer's own keys** name what a pointer touched and a keyboard can't: `row:<i>`, `option:<i>` (the pause menu's options, beside its rows; why a list of its own: [[INVARIANTS]] § Input), `level:<n>`, `language:<code>`, and the explore HUD's party column, which names a card by its species, never its place, since a drag can re-sort the column under a resting finger: `bundle:<species>` (a card of one animal: it goes first), `open:<species>` (a card of several: open or close it), `animal:<id>` (an animal on an open card: it goes first), `move:<species>:<to>` (a card dropped at place `to`; the HUD presses it itself on the drop, and gives the carried card another key meanwhile, so the drag is never also a tap). A key handler reads them with `tappedRow` and its siblings beside the keys it knows. A row key on the battle's menus only moves the cursor (`menu.ts`), since a pick there spends the turn; elsewhere it moves the cursor and then runs the handler's own Enter.
- **Touch controls** are drawing only: `touch.on` decides whether the D-pad, the number pad, the tap hints and the finger-sized rows show (`:root.touch` in the CSS), never what a press does.
- The pretend key events are untrusted (`isTrusted` false), and `watchInput` ignores them: the page's own presses never switch the touch controls off. They carry no `code`, so the `Keyboard` files a D-pad's held arrow under its key name.

### Sound

```
 battle / doctor / pause / title     ┐                          ┌ master (MASTER_VOLUME)
 controllers, hud (a new lead)       ┴─ sfx.play(cue, opts) ───┤   → limiter → speakers
 cues.ts (data) ─ scheduleCue ─────────────── WebAudio nodes ───┘
```

- **Where a cue plays.** From the screens, where events already become visuals: a beat of the battle or the doctor plays its cue as it runs, a key that moves a cursor or picks something plays its blip, the HUD dings when a party edit makes a new lead. The authority and the engine never hear of sound ([[DECISIONS]] § Client), so a `RemoteAuthority` changes nothing here. The cue table is [[UI_SPEC]] § Sound and juice.
- **When sound can start.** `main.ts` calls `sfx.unlock()` in the capture phase of every `keydown`, `pointerdown`, `pointerup` and `touchend`, before any screen sees the key, so the key that opens a menu can already blip (a finger's tap presses as it lifts, the moment a browser counts a touch as the player's). `unlock` makes the `AudioContext` only on a press the browser counts as the player's (`navigator.userActivation.isActive`): Chrome does not count Escape or the modifier keys, and a context made on one of them logs a warning (which would fail `scripts/screenshot.mjs`).
- **The setting.** `sfx.on`, remembered in `localStorage['animath.sound']` (`'on'` / `'off'`; storage failures ignored), on by default. M is `main.ts` calling `sfx.flip()`, which plays no cue: the sound chip shows what happened. Off disconnects the master gain (whatever was playing ends unheard) and suspends the context; on makes a fresh master and resumes it.
- **Without WebAudio** or in tests, `play` records the cue (`recent`, `onCue`) and schedules nothing. Tests listen with `sfx.onCue`; nothing in them unlocks a context.

### Coordinate system

Engine grid `(x, y)` maps to Three `(x, height, z)` with `z = y`; grid "down" is screen-down because the camera's yaw is fixed. Each tile is a 1 × 1 column centred on integer `x`, `z`, from `y = −0.5` up to its ground top, which is at `y = 0.5 + 0.25·height` for land and lower for water (`groundTop` in `tiles.ts`). Figures stand with their feet on that top face; the player hops 0.15 during a step. A figure faces `+z` (grid "down", toward the camera) at `rotation.y = 0`; `up` is `π`, `right` is `π/2`, `left` is `-π/2`.

### Modes

Two modes, one on screen at a time. `battle-started` hands the screen to the battle controller: explore input is switched off, the world keeps drawing for a moment so the step into the grass lands while the iris closes on it, then the battle scene and panel replace it under the iris opening. The authority resolves each battle intent at once (`battle-updated`); the controller plays the events back as beats and only then shows the new state, so the screen lags the authority on purpose. `battle-ended` puts the authority back in explore at once, but the screen stays on the result card until the player leaves it; only then does explore input come back. Walking during a battle and battle intents outside one are ignored by the authority; party intents during one are refused by the engine (`not-exploring`), because the battle holds its own copy of the party and writes it back at the end.

The pause menu is not a mode either: an overlay in explore, opened by Escape, that switches explore input off while it is open and closes itself on `battle-started`, `doctor-visit-started`, `welcome` or `game-left`. The authority does not know it is open; it sees only the party intents the menu sends, and `leave-game` from its Start screen row.

The title is before the modes: no game is under way (`game.mode` is `loading` before the first one and `title` after `game-left`), and `title.open` takes every key. Its world is the renderer's, pointed aside and drifting (`lookAt`), with scenery figures that go on `welcome`; its starter stage is drawn instead of the world, as a battle scene is (`setStage`). It closes on `welcome`: Continue's `start({ game })` or a `new-game` the authority accepted.

The doctor is not a mode: a dialogue card over explore, driven by `doctor-visit-started` / `-updated` / `-ended` (the doctor controller plays each update back as beats, like the battle screen). Each doctor event carries its visit's number (a `DoctorState`'s `step` starts at 0 every visit), and the card ignores events of any other visit, as the battle screen ignores other battles'. The world keeps drawing under it; explore input is off while it is open, and the authority ignores walking during a visit and doctor intents outside one. The authority opens a visit on `interact` when `canTalkToDoctor(seed, pos, facing)` holds, so it tracks the facing the client shows: `down` in a new game, then the `dir` of every `move`, walked (`player-moved`) or blocked (`player-blocked`), and the `dir` of `taken-to-doctor`. The facing is saved with the game and `welcome` carries it, so a restored player looks the way they did and both sides agree after any `welcome`. The client computes the "Press Enter to talk to the doctor" prompt with the same engine function from the same events. After a lost battle the authority emits `battle-ended` and then `taken-to-doctor`, which puts the player beside the tent without a tween, turns them to it and replaces the party; the battle screen's result card ("Good try!", with no closing line) waits on top meanwhile, and the message line words the doctor's line from `taken-to-doctor`. `player-placed` (a move without a tween that keeps the facing) is in the protocol, but nothing sends it today. See [[UI_SPEC]].

### Saving

Local first ([[DECISIONS]] § Saves). The pieces:

```
 LocalAuthority ──events──▶ Autosave.handle ──(one per intent)──▶ commit()
       ▲                        │                                   │
       │ start({ game })        │ snapshot()                        ├─▶ localStorage['animath.save']   the save
 Autosave.boot() ◀── localStorage (instant) · server GET (only       │    (compare-before-write)
       │               when there is an identity but no save)       └─▶ PUT /api/players/:id/save      the backup
       └─▶ notice (a copy key for the HUD)                               (background, seq must rise)
```

- **The document.** `SaveV1` (engine `save.ts`): `version`, `seed`, `pos`, `party` since the first save; `facing`, `steps`, `visits` (doctor visits opened, which with `steps` key each visit's puzzles), `lineage`, `seq` on every write since client saves; `battle` while one is in progress. A doctor visit is not saved: a reload closes it, and what it healed is already in the party. `lineage` is a random id minted when a game starts, the same in every save of that game; `seq` numbers the saves of a game, one higher each time. Old documents lack the later fields and `restoreGame` fills them in (facing down, no steps, no visits).
- **When.** `Autosave.handle` marks the save dirty on every event that changes the game (a step or a bump, a battle start, turn or end, a party change, a doctor visit) and writes once, in a microtask, after everything one intent caused. `flush()` writes at once on `pagehide` and when the page is hidden. Events emitted before `begin()` are the authority starting from the plan and write nothing. The title writes and sends nothing: saving starts with `begin()` (Continue) or with a new game's `welcome`, and `game-left` writes what is dirty, sends the backup and stops it.
- **A new game** (`welcome` with `newGame: true`, from the title) is a game of its own: a fresh lineage, no extras, its `seq` numbered on past every save the page has seen and past whatever the key holds when it first writes. That first write moves the key's text (the game the kid left, or another tab's later save of it) to the first free `animath.save.previous` slot (up to 200, where the accidental set-asides keep 20), never over one; with none free the key keeps the old game and this one is not saved in the browser. Picking a starter counts as playing, so an unreadable save waiting in the key goes to `animath.save.unreadable` at once. The lineage the kid left is remembered for the page (`putAway`): the server's copy of that game never replaces the new one (saves jump past it, and the server keeps it in `save_backups`), while any other game the server holds is settled by the usual rule, so a game the title never showed is never put away unseen.
- **Continue** starts the authority from `resumable()`: the save the page carries on from as it is now (the one it loaded, last wrote, or took on from another tab's walk while the title was up), not the game the title first showed.
- **Compare before write.** Every tab keeps the exact text of the save it last read or wrote. Before a write it reads the key again: unchanged → write. Changed → another tab saved. If that save differs from this tab's own only in whereabouts (`sameProgress`: position, facing, steps, visits, lineage, seq), this tab carries on from it (its `seq`, its lineage, and its step and visit counts, which `LocalAuthority.catchUp` raises so encounters and doctor puzzles follow on, with the doctor's card open too, and in a battle, which it re-keys from the new count) and writes on top. Otherwise this tab is behind: it stops writing, locally and to the server. The check is not atomic across tabs: a page's view of `localStorage` is brought up to date only between tasks, so two tabs writing in the same instant both pass it, and the first write is lost. A page that finds itself behind while its own last save is neither the save now in the key, nor played on from (the same lineage, a higher `seq`), nor kept aside anywhere, keeps it in `animath.save.replaced` (`keepOwnSave`). So does a page whose `storage` event carries a save of its game numbered no higher than its own last one, and not it: that save went over this page's unseen, even when the key has moved on since (`overwrittenUnseen`). `behind` says why, from the save that put it behind, whichever page notices: `window` when that save is still this tab's game (the same lineage) played on elsewhere, `replaced` when another game has taken its place (a tab that took a bigger game from the server into the browser's save, and every other tab of the old game, as after a new game from the title), `gone` when the key has gone. From then on `main.ts` runs no controller and lets no key reach the game; only the browser's own keys pass (with Ctrl, Alt or Cmd, and F1–F12). It cancels `beforeinput` too, so nothing typed with AltGr or Option, pasted or dropped reaches the name box (only an input method's composition cannot be cancelled). Each frame it asks `behindAction` (`save/behind.ts`) what to do. Hidden, the page waits to be shown. Behind another window, it reloads into the newest game when it is in use (visible and focused); on screen while another window is in use, it shows the behind card and waits for the kid. Behind for another reason, it reloads as soon as it is visible. A page reloads itself at most `RELOADS_PER_MINUTE` (3) times a minute, so no bug can trap a kid in a loop of reloads, and past that it shows the card. Enter, Space outside a text box, or the card's button reload whatever the count, because the kid asked, and do not count. A reload that catches up with another window in the middle of a game leaves a note in `sessionStorage` (`animath.caughtUp`), and the reloaded page skips the title: it does Continue at once and says "You were playing in another window. Here's your newest game!" (`save.caughtUp`) instead of "Welcome back!". A page that was on the title reloads into the title. A `storage` event runs the same check at once, against the key as it is, never the value the event carried. A page that may have missed events runs it again (`recheck`): on `pageshow` back from the back/forward cache, on `resume` after the browser froze it, and when its window gains focus. A key that has gone (site data cleared) is never written back.
- **Start** (`boot()`), whose plan the title shows: its game is Continue's. A readable local save → that game, and `welcome back` once Continue picks it up. A newer build's save → no game; a new one writes nothing (`frozen`), and the title says why. An unreadable save → no game; the new game leaves the key alone until the kid has played (a starter picked, a battle ended, the party changed, or an edit to it was accepted; a doctor visit alone or a refused edit is not playing), then moves the old text to `animath.save.unreadable` and writes (`held`). No readable save but an identity → one `GET` (2.5 s at most): a readable backup becomes the game (and the local save at its first write); an unreadable or newer one gives no game, with that notice. Otherwise no game and a fresh lineage, until New game.
- **The backup.** A tab that saves locally also sends its latest document: 1 s after something that matters, 15 s after walking, with `keepalive` on `pagehide` and when the page is hidden; one request at a time. No identity yet → `POST /api/players` first (a second tab that made one first is used instead). With an identity from before, the first thing sent is a `GET`, and the save with the higher `seq` carries on: this tab's is sent; the server's (another game played more, or this game's saves that never reached this browser's storage) is adopted — the local one moved to `animath.save.replaced` — and the page reloads into it. An answer that finds the key changed by another tab whose storage event has not come yet carries on from that tab's walk first, and settles again. A tie between two games goes to the server's, and only between saves: at `seq` 0 neither has one, so nothing is adopted. A `409` settles the same way. An unreadable backup is saved past once the kid has played (the next `seq` beats it; the server keeps it), and a browser that found only that at start says its saved game did not load; a newer build's backup is never written over. Out of reach: retries at 2, 4, 8, 16, 32 s, then rest, with no timer, until a battle ends or the party changes. A `400`/`413` is a bug: one `console.error`, and no more backups this visit. `401` or `404 no such player`: the identity moves to the first free slot of `animath.player.previous` (`.2`, `.3`, …, never over one kept before) and a new player is made. Every one of these is decided from the API's own JSON answer; a page from anything in between (a tunnel's warning page, a proxy's error or login page) counts as out of reach, whatever its status.
- **Keys** (`save/storage.ts` `KEYS`): `animath.save`, `animath.player` (`{ id, secret }`), `animath.save.unreadable`, `animath.save.replaced`, `animath.save.previous` (a game left for a new one on the title), `animath.player.previous`. `animath.save.replaced` also takes a page's own last save when another tab wrote over it in the same instant, unseen (§ Compare before write). A save set aside goes to the first free slot of its key (`animath.save.unreadable`, then `.2`, `.3`, … up to `.20`) and is never written over; with no slot free, the save it would have made room for stays where it is and this game is not saved in the browser. The language's `animath.language` belongs to the copy module.
- **`?new`, `?party=` and `?zoo`**: no store, no server: a throwaway game that skips the title and reads and writes nothing.

### Data model

- `players` — `id uuid pk`, `secret_hash text` (SHA-256 of the client-held secret; the secret itself is never stored), `display_name text?`, `created_at`, `last_seen_at` (bumped on every authenticated request). One row per anonymous player.
- `saves` — `player_id uuid pk → players (cascade)`, `data jsonb` (the `SaveV1` envelope below), `updated_at`. One save per player: the backup of the save that lives in the player's browser.
- `save_backups` — `id bigserial pk`, `player_id uuid → players (cascade)`, `data jsonb`, `reason text` (`replaced`: a different game took its place; `unreadable`: this build could not read it), `created_at`. A save the server would otherwise lose, copied here before a write replaces it. Nothing reads it; it is for recovering a kid's game by hand ([[DEVELOPMENT]] § Database).

Hot fields get promoted from `data` to columns when a query needs them (nearby players, leaderboards).

### HTTP API

Errors are JSON `{ error: string }`, except the health check's. All routes are under `/api`.

| Route                         | Auth  | Response                                                                          |
| ----------------------------- | ----- | --------------------------------------------------------------------------------- |
| `GET /api/health`             | none  | `200 { ok: true, db: true }`, or `503 { ok: true, db: false }` when the database does not answer. |
| `POST /api/players`           | none  | `201 { id: uuid, secret: string }`. The client stores both; the secret is shown once. |
| `GET /api/players/:id/save`   | owner | `200 SaveV1` as stored, readable or not, or `404 { error: 'no save yet' }`.        |
| `PUT /api/players/:id/save`   | owner | `200 { ok: true }` after the write; `400` bad JSON, or a document `validateSaveWrite` refuses; `409` when the stored save's `seq` is the same or higher; `413` body over 1 MiB (`SAVE_MAX_BYTES`). |

**Owner auth** is `Authorization: Bearer <secret>`. Missing or malformed header → `401`; `:id` unknown (or not a uuid) → `404 { error: 'no such player' }`; secret does not match the stored hash → `401`. The client tells the two `404`s apart by their `error` text, which `players.test.ts` pins.

**`SaveV1`** (engine `src/save.ts`) is a versioned envelope, stored and returned verbatim:

```ts
{
	version: 1,
	seed: number,                  // integer; the world is a pure function of it
	pos: { x: number, y: number },  // integer tile coordinates, any sign
	party: AnimalInstance[],       // any number, in species bundles, of { id: string, speciesId: string, nickname?: string, hp: number }
	// Optional in SaveV1, so old documents still read; required in a write (`SaveWrite`):
	facing?: 'up' | 'down' | 'left' | 'right',
	steps?: number,                // whole; the authority's step count, which keys every encounter
	visits?: number,               // whole; doctor visits opened, which with steps key each visit
	lineage?: string,              // 1–64 characters; the game this save belongs to
	seq?: number,                  // whole ≥ 1; this save's number within its game
	battle?: unknown               // the battle in progress (a BattleState), checked on load by readBattle
}
```

`version`, `seed`, `pos` and `party` are validated strictly (`speciesId` must be in the engine catalog, `hp` a whole number ≥ 0, `id` unique within the party); `facing`, `steps`, `visits`, `lineage` and `seq` when present, and a write must carry all five. `battle` only has to be storable: the client checks it when it loads (`readBattle`) and drops it if it cannot be picked up. Any extra field — top-level or per animal — is stored and returned as sent, so a newer client can add data without a server change; bump `version` only when an old document becomes unreadable. "As sent" is JSON semantics: key order and `-0` are not preserved, and a document containing a NUL character, a lone surrogate or a number that overflows to Infinity is a `400`, not a mangled row.

**The write guard** (`canReplace`, `replacesAnotherGame`, `writeSave`). A `PUT` lands only when its `seq` is higher than the stored save's (`saveSeq`: its `seq`, or 0 when it has none or cannot be read); otherwise `409`. Within one game that puts backups in order however the network delivers them, and the browser's compare-before-write keeps a game's saves in one line (§ Saving). Between two games (two lineages: one started while the other was out of reach), the one saved more often wins. Before a write replaces a save from a different lineage, or one `readSave` cannot read, the old document goes to `save_backups`. The read, the decision and the write run in one transaction with the player's row locked, so of racing writes one lands and the rest see it.
