# Invariants

What must stay true at runtime, and the failure that taught it.

**Admission test: could you write a test that fails when this stops being true?** If yes, it belongs here. A choice among alternatives goes in [[DECISIONS]]. Where code lives goes in [[ARCHITECTURE]]. Anything a player can observe goes in [[PRODUCT]]. A fact that is here is not in those files — a second copy drifts, and the two disagree silently.

**One entry per invariant.** The `###` heading states the rule, phrased so it can be violated. Under it: the mechanism that enforces it, and the incident that made it necessary (or "design-time" when it was set before any incident).

An entry that no longer matches the code is a bug in one of them. Find out which before you trust it.

---

## Engine purity

### The engine imports nothing from outside its own package

No DOM, no Three.js, no Node built-ins, no npm packages. It must run byte-for-byte identically in a browser and on the server, because multiplayer moves the authority from one to the other. Enforced twice: `packages/engine/tsconfig.json` has `lib: ["ES2022"]` and `types: []`, so a reference to `window` or `process` fails to compile; `test/purity.test.ts` scans every source file and fails on a non-relative `from` import (a bare `import 'x'` or an `import('x')` would pass it). Design-time.

### The engine never reads ambient randomness or the clock

Every random draw goes through an `Rng` the caller constructed from a seed, and nothing reads `Date.now`. A battle, a chunk, a puzzle can then be replayed exactly from `(seed, intents)`, which is what lets a client predict and a server verify without disagreeing. Enforced by `test/purity.test.ts` (comment-stripped source grep) and by `rng.test.ts` / `world.test.ts` / `puzzles.test.ts` asserting equal output for equal seeds. Design-time.

### The engine holds no player-facing words

Species and attacks are ids; events say what happened; a refusal is a code; a `message` line is a copy key from `LINES` with numbers and species by id. A sentence written in the engine would reach a Danish kid in English, and would have to be shipped twice once a server authority sends it. Enforced by `test/no-words.test.ts` (TypeScript's parser over every source file but `save.ts`, whose validator messages are for developers: no literal that reads as a sentence outside `new Error`), by the battle and doctor sweeps (`words.ts`: no worded string in any state or event, nicknames aside), by the types (`LINES` gives each param a kind, a species or a number, and `Line` is typed from it), and on the client by `messageWords`, which takes nothing else from a `message` line. Design-time.

### A chunk is a pure function of `(seed, cx, cy)`

Generating chunk `(4, −2)` alone yields the same tiles as generating it after `(3, −2)`, and tile `(x, y)` is the same whether asked via its chunk or via `tileAtWorld`. Per-tile randomness is derived from `hashInts(seed, x, y, …)`, never from a shared generator whose state depends on call order. Enforced by `world.test.ts` ("pure function", "no seams"). Design-time.

## Puzzles

### Every puzzle's answer is a whole number and matches its prompt

For every kind, at every difficulty in the kind's declared range, `answer` is an integer and an independent re-solve of `prompt` yields it. Division builds the dividend from the answer; square roots square the answer; sequences are generated from a closed form. Enforced by `puzzles.test.ts`, which re-parses each prompt with its own solver over 200 puzzles per (kind, difficulty), each difficulty from its own fixed seed. Design-time.

### Operands climb with difficulty: every band has a floor, and both ends are non-decreasing

For every kind but `sequence`, the smallest and the largest number shown in a prompt are non-decreasing in difficulty (per operation, since `missing` mixes "+ ?" and "× ?"), nothing above difficulty 1 is "+ 1" / "× 1", ten is never a factor, and a puzzle at difficulty `d` shows a bigger number than any puzzle at `d − 2`. For sequences, each pattern's first term has both ends non-decreasing in difficulty and a floor above its ceiling two difficulties down (so no sequence is asked at `d` and at `d − 2`), each pattern's smallest answer never falls, and only difficulty 1 counts by ones. Operands, steps and first terms are drawn from `[lo, hi]` bands (`arithmetic.ts`, `sqrt.ts`, `sequence.ts`), never from `[1, max]` or `[0, max]`. Enforced by `puzzles.test.ts` § difficulty ladder, sampled over 300–900 puzzles per (kind, difficulty) from fixed seeds. Incident: #7 — operands had ceilings only, so a difficulty-3 attack asked "4 + 1", "16 − 15" and "8 + ? = 9" three puzzles in a row, and difficulty 10 could ask "√9", "1, 1, 2, 3, ?" or "0, 10, 20, 30, ?".

### A sequence prompt has exactly one right answer

Every sequence prompt fits exactly one of the patterns a kid is taught — equal gaps, a constant ratio, adding the last two, gaps that grow by a constant — and its last three numbers are evenly spaced only when the whole prompt counts, so the generator's answer is the only right one. Add-the-last-two never starts with a pair `a, b` where `2b = 3a` (its gaps then also grow by a constant) or `b = a` (it then ends in a counting run). Enforced by `puzzles.test.ts` ("no prompt fits two patterns"), which reads every prompt with each pattern, and with "count on from the last three", independently of the generator; sampled over 900 puzzles per difficulty from fixed seeds. Incident: PR #10 — "2, 3, 5, 8, ?" was asked at difficulty 7–10 expecting 13, while "the gaps grow by one" answers 12; "4, 4, 8, 12, ?" expected 20 where counting on says 16.

### An attack's description names exactly what its puzzles can be

The sentence about the highlighted attack lists the engine's `puzzleTopics(kinds, difficulty)` for that attack at its level, and every topic listed must be one a puzzle there can have, and every topic a puzzle there can have must be listed. The starter's Scurry Kick on hard said "adding, taking away or missing numbers" and asked "7 × ? = 56": a missing number sat in a times table, and the words came from the attack's kinds, not from what the generator produces at that difficulty (QA, the i18n PR). Enforced by `puzzles.test.ts` ("what an attack says it asks": every species × attack × level and every kind × difficulty, the topics met over 300 seeds, read from the prompts by an independent classifier, equal the topics promised) and by `copy-files.test.ts` (every topic has its words). Design-time.

### Answers are judged in the engine, never in the UI

`checkAnswer(puzzle, input)` is the only place a submitted answer is compared. The UI passes the raw string through; the authority calls `checkAnswer` and emits the result. When the authority moves to the server, a client cannot claim a hit it did not earn. The engine half is enforced by `battle-reducer.test.ts` ("a wrong answer never damages the opponent, whatever the input") and `doctor.test.ts` ("judges only with checkAnswer, whatever the input"); the client half only by review (grep the client for `=== puzzle.answer` / `.answer ===`), which Phase 2.5 skips for a client-only diff. Design-time.

### Every right answer adds exactly one to the puzzles solved, and nothing else moves it

Every reducer that judges an answer (a wild battle, a doctor visit, a friendly match) says so in exactly one `answer-judged` event, and the engine's `countSolved` reads the count from those events: one more for each that was right, and in a match only for the answers of the side it is asked about. `LocalAuthority` applies it to every battle and doctor step and says `solved-changed` (the whole count) right after the `battle-updated` or `doctor-visit-updated` that judged the answer; a friendly match's events are to reach it through `countMatchAnswers(events, side)`, each batch once (a batch passed twice counts twice), when the match screen that calls it lands. So a wrong answer, a refused intent, backing out or leaving adds nothing, the count never goes down, a hand-over of many animals counts once, and the other player's answers never count for this one. The count is in `snapshot()`, the save and `welcome`, goes along on `travel`, and starts at 0 in a new game; it stops at `Number.MAX_SAFE_INTEGER`, the most a save holds. Enforced by `solved.test.ts` (battles of every species pair, doctor visits with every kind of sum, and matches from both sides, answered in forms `checkAnswer` takes and refuses, the kid deciding right or wrong before answering) and `local-authority.test.ts` § puzzles solved (a long game: the count is exactly the right answers judged, one at a time, and the view agrees; saved mid-battle and picked up; a new game at 0; a match's events for one side and the other). Design-time: #94.

### Difficulty is monotonic in tier and attack index, and strictly increasing in level

`puzzleDifficulty(tier, n, level)` never decreases when the tier or the attack index increases, and `(1, 1, 1)` maps to 1 while `(5, 4, 3)` maps to 10. Within an attack every level asks exactly one difficulty more than the level below it, and hard never passes 10, so a level that hits harder always asks at a higher difficulty. (The puzzles themselves can overlap between neighbouring difficulties; § "Operands climb with difficulty" promises bigger numbers only two difficulties apart.) This holds because an attack's easy level is capped at 8 before the levels are added; a clamp on the finished difficulty would fold the top levels together instead. Enforced by `puzzles.test.ts` § difficulty mapping: every attack in the catalog asks a harder puzzle wherever it hits harder, and any tier's first eight attacks climb one step per level. Incident: #32. The final clamp at 10 gave a bear's Maul and Crush difficulty 10 on medium and on hard, so medium asked the same sums for less damage.

## Battle

### Within a species, damage strictly increases with attack index and with level

With `solved` true, `attackDamage(spec, n, level, solved)` is strictly greater than `attackDamage(spec, n−1, level, solved)` and than `attackDamage(spec, n, level−1, solved)`; attack N at level 3 is the species maximum and attack 1 at level 1 its minimum. Holds because `power` strictly increases along `attacks` and the level multipliers `[1, 1.6, 2.4]` are increasing; rounding cannot break it as long as every power is at least 2 (a power of 1 rounds to 2 at both level 2 and level 3) and consecutive powers differ by ≥ 1. Enforced by `battle.test.ts` over every species in the catalog — a new species with a non-increasing power table fails the suite. Design-time.

### A wrong answer deals zero damage

`attackDamage(…, solved = false)` is 0. No partial credit, no consolation hit. In the reducer, an `answer-judged` with `correct: false` is followed by `missed`, never by a player `hit`, and the opponent's HP is unchanged — for any input, including an empty string; a correct one is always followed by a `hit` for exactly `attackDamage`. Enforced by `battle.test.ts` and `battle-reducer.test.ts` § answers over every species pair. Design-time.

### A battle is a pure function of `(seed, party, wild, leashQuality, intents)` and never mutates its input

`applyBattleIntent(state, intent, seed)` returns a new state and leaves the one it was given untouched; the Rng for the n-th accepted intent is `new Rng(hashInts(seed, n))`, so replaying the same intent log from the same seed yields identical states and events, and a rejected intent (wrong phase, bad attack index or level, a switch to nobody, not an object) returns the same state reference with a single `rejected` event. The seed is passed by the authority on every call and is **not** in `BattleState`: the state goes to the client, and a client that knew the seed could predict every leash roll and every wild attack. This is what lets a client and a server agree without trusting each other. Enforced by `battle-reducer.test.ts`: the catalog sweep deep-freezes every input state, the replay test plays every species pair from the same seed twice and compares, and a test asserts the state has no `seed` key. Design-time.

### A battle ends with probability 1, and HP stays a whole number in `[0, maxHp]` on both sides

Every round the wild animal either hits for its attack's `power`, which is ≥ 1 for every attack in the catalog, or misses, which it can only do against an animal of its own tier or fiercer and then with probability `WILD_MISS_CHANCE` = 0.44 < 1. So each round the party's total HP falls by at least 1 with probability ≥ 0.56 whatever the player answers, and a party of total HP `H` is knocked out within a finite number of rounds with probability 1 (expected at most `H / 0.56` rounds against a player who never hits). Every action on the player's turn — an answered attack, a leash that breaks free, a switch — either ends the battle or hands the wild animal a turn; the one free action, picking who replaces a knocked-out animal (`choose-animal`), happens at most once per knock-out, and nothing stands a tired animal up again mid-battle, so no sequence of switches can stall a battle. Damage is clamped at 0 and `startBattle` refuses an animal outside `0..maxHp`, or two animals sharing an id (a duplicate would give the party phantom HP and make writing HP back ambiguous). Enforced by `battle-reducer.test.ts` over every species pair × 25 seeds with a 60%-accurate random player who also throws the leash, switches animals and occasionally runs, so every outcome is reached, by § switching's player who switches whenever anyone else is standing (always lost, the wild animal untouched), and by `battle.test.ts` (`power ≥ 1`). Design-time; restated when wild misses arrived (the round no longer always costs HP) and when switching did.

### A wild animal misses only an animal of its own tier or fiercer, and exactly when its roll says so

On its turn the wild animal draws its attack (`rng.int(1, N)`) and then a miss roll (`rng.next()`) from the intent's Rng, both every turn; it misses exactly when its tier is ≤ the tier of the party animal in front *on that turn* and the roll is below `WILD_MISS_CHANCE`, emitting `missed { attacker: 'opponent' }` and leaving the party's HP unchanged. Because the miss roll comes after the attack pick and nothing draws after it, every turn against a smaller animal draws and hits exactly as it would if misses did not exist, so a battle in which every animal that fights is smaller than the wild one plays exactly as if wild animals never missed; once a bigger party member steps in, by a switch or after a knock-out, its turns can miss. Enforced by `battle-reducer.test.ts` § the wild animal, which recomputes both draws for every species pair over 40 seeds and checks a fox that knocks out a squirrel and then misses the bear that steps in at the expected rate, by § switching, which recomputes the reply to a switch against the newcomer for every species trio, by the catalog sweep, and by the seed-2024 golden replay (a fox against a squirrel and a rabbit). Incident: PR #8's balance table — with wild animals that never missed, a kid on the easiest puzzle who was always right beat an animal of their own tier 15% of the time.

### Only a `switch` changes the animal in front, and a switch changes no HP by itself

`active` changes only when a `switch` intent is accepted, and `canSwitchTo(state, i)` — the one rule the reducer and the client's party list both use — accepts it only while the player is choosing (`choose-action` or `choose-animal`) and only for a party member that is standing and not already in front. A switch on the player's turn is followed by the wild animal's reply against the newcomer, which is the only HP change in that step; a switch that replaces a knocked-out animal changes no HP and gets no reply. A tired animal never comes back in, and a switch mid-puzzle is refused, so switching can neither dodge a committed attack nor revive anyone. Enforced by `battle-reducer.test.ts`: the catalog sweep checks on every step that `active` moves only with a `switched` event from a `switch` intent and that no party member the wild animal did not hit changes HP; § switching recomputes the reply for every species trio and checks `canSwitchTo` against the reducer on every state of a switching player's battles; § rejected intents covers the animal in front, a tired one, missing and non-integer indices and a puzzle in progress. Design-time.

### Only an animal that can go where a battle is fought ever fights in it

A battle carries its realm (`BattleState.realm`: land, or the water from the boat), set when it starts and never changed. `startBattle` sends out `leadIndex(party, realm)`, the first animal standing that can fight there (`canFightIn`), and refuses a battle with none, or against a wild animal that can't fight there; `canSwitchTo` refuses one that can't (`cannot-fight-here`); and the battle is lost once no animal that can fight there is standing, whoever else still stands in the boat. So out on the water a squirrel never fights, and never keeps a battle going that the swimmers have lost. Enforced by `battle-reducer.test.ts` § on the water (who starts, the refusals, the loss with animals standing in the boat, and random battles against every animal of the water in which every step's animal in front swims and nobody in the boat loses HP), and `save.test.ts` (a battle on the water picked up only out on the water, with a swimmer in front against a wild animal that swims). Design-time: the human's rule, "you can't fight on water unless you have an amphibious animal".

### What the battle screen previews is the hit that lands

The hit badges, each level's damage on the level picker, the lighter segment on the wild animal's HP bar and "That would tire it out!" come from the engine's `attackDamage` and `landHit`, called on the state on screen, and the reducer lands a right answer through the same `landHit`: the preview shows exactly the damage and the HP left that the hit then takes, and "tire it out" exactly when the hit knocks the animal out and wins. Enforced by `battle-reducer.test.ts` ("landHit, as a screen previews a hit, is exactly the hit a right answer lands": every species × attack × level against a wild animal at full HP and at every HP round the hit); the client half, that the panel computes no damage of its own, by review. Design-time.

### A catch happens only on a leash throw whose seeded roll beats `catchProbability`

`leash-thrown.success` is exactly `rng.next() < catchProbability(hp / maxHp, catchRate, leashQuality)` with the battle's own Rng, a success ends the battle `caught` with the wild animal at its current (non-zero) HP, and a failure hands the turn to the wild animal. Enforced by `battle-reducer.test.ts` § the leash, which recomputes the roll independently for every species at four HP bands. Design-time.

### Catch probability is non-increasing in HP fraction and never a certainty

`catchProbability(hp, rate, leash)` is monotonically non-increasing in `hp`, halves every 0.2 of HP, and is capped at 0.95 regardless of leash quality. Enforced by `battle.test.ts` § catchProbability. Design-time.

## Match

### A match ends when a side has no animal standing, or a player leaves or times out

The sibling of § "A battle ends with probability 1": a match has no wild animal whose attacks always come, so its end rests on the players. A right answer hits an animal that is standing for at least 1 (every power is ≥ 1), nothing in a match raises HP, and a knock-out that leaves its side someone standing asks only for a free pick, so a match lasts at most as many right answers as both teams have HP, and ends with probability 1 as long as both kids keep playing and either is right some of the time. `leave` and `timeout` end it at once, from either side, in every phase. There is no draw and no turn limit: two kids who never answer right, or only switch, play on until one of them leaves, and a kid who stops sending anything (walks away mid-puzzle, say) holds the match until the other leaves or the authority reports them gone with `timeout`, which it may do for a dropped connection or, with a turn clock of its own, for a turn sat on too long. Enforced by `match.test.ts`: random matches between kids right 20–100% of the time, who switch, leave and time out, all end, with no more hits than HP; a kid who switches whenever they can never stalls one; leaving and timing out work in every phase; two kids who only switch still play after 500 turns and stop the moment one leaves. Design-time.

### Only the side whose turn it is acts, and turns alternate

Every phase but the end names the side that acts, and an attack, an answer, a switch or a pick from the other side is refused (`not-your-turn`); only `leave` and `timeout` are taken from either side. An answer, right or wrong, and a switch pass the turn and add one to `turn`; an attack, a pick after a knock-out and the end do not, so the side that started plays exactly the odd turns. Enforced by `match.test.ts` § turns, and by the random matches, which check the side that acts against the turn's parity after every step. Design-time.

### No match view or event ever holds a puzzle's answer

The state keeps the open puzzle, answer and all, and never leaves the authority. A player is sent `matchView(state, side)`, built field by field (never by spreading the state) with the puzzle as a `ShownPuzzle`, and the events, in which `puzzle-shown` carries a `ShownPuzzle` and `answer-judged` only whether the answer was right; so both players get the same events. An answer on the wire would be one look in the browser's tools away from any kid; without it, a kid has to do the sum. The redaction does not make cheating impossible: every prompt is plain arithmetic, which a modified client could work out by itself, and a match that changes nothing gives it nothing to win. Enforced by `match.test.ts`: the random matches scan every view of both sides and every event for a key named `answer`, and check that every view of a puzzle in progress stays the same when its answer is swapped for another, so no field can carry it under another name. Design-time: the human's rule, the waiting player sees the puzzle without its answer.

### A match is a pure function of `(seed, parties, (side, intent) log)`, never touches the parties, and keeps its seed out of its state

`applyMatchIntent(state, side, intent, seed)` returns a new state and leaves the one it was given untouched. The coin is `new Rng(hashInts(seed, hashString('coin')))` and the n-th accepted intent draws from `new Rng(hashInts(seed, n))`, so the same log replays to the same states and events, which lets a server log a match and replay it. A refused intent returns the same state reference with a single `rejected` event. `matchTeam` and `startMatch` copy what they take, so nothing a match does can reach a player's party. The seed is the authority's and never in `MatchState`. Enforced by `match.test.ts`: the random matches deep-freeze every party and state and try a wrong intent at every step; the replay and golden tests; and the start, which holds no seed. Design-time.

### A match asks and hits exactly as a wild battle does

Both reducers play an attack through `battle/attack.ts`: the puzzle at `puzzleDifficulty` of the attacker's own tier, attack and level, of a kind the attack can ask; the answer judged only by `checkAnswer`; a hit of `attackDamage`. So a right answer in a match deals exactly the formula's damage and a wrong one nothing, for any input, and a change to how an attack asks or hits changes both. Enforced by `match.test.ts` § an attack, over every land species × attack × level against the formulas with twelve inputs, right and wrong, and by the battle reducer's tests, which pass unchanged through the same code (the seed-2024 golden battle included). Design-time.

## Authority

### The authority's randomness is keyed by the world seed and its step count, and its seeds never leave it

`LocalAuthority` rolls one encounter after each completed step with `new Rng(hashInts(worldSeed, hashString('encounter'), steps))`, gives a battle the seed `hashInts(worldSeed, hashString('battle'), steps)` of the step it started on, and gives the n-th doctor visit of the game the seed `hashInts(worldSeed, hashString('doctor'), steps, n)` (so leaving and talking again on the same tile asks new puzzles); nothing in it reads ambient randomness or the clock except `mintId`, whose `crypto` call makes an animal's id, which must be unique rather than replayable. So a walk replays — the same steps meet the same animals and the same puzzles, at the doctor too — which is what lets a server running the same code agree with a client. The battle and visit seeds stay in the authority: events carry only `BattleState` and `DoctorState`, which have no seed. A save holds the step and visit counts, from which the seeds are derived again on load, never a seed itself. Enforced by `packages/client/test/local-authority.test.ts` ("a walk meets the same animals and puzzles at the same steps, each with a fresh id", "a visit replays from the same intents, and a second visit asks new puzzles", "a doctor visit never shows its seed") and, for the states, the engine's `battle-reducer.test.ts` and `doctor.test.ts`. Design-time.

### A game picked up from a save plays on exactly as if the page had never reloaded

`snapshot()` holds everything the authority's next event depends on — the world the player is in (its seed is `worldSeed(world)`), position, facing, the step and doctor-visit counts, the party, the puzzles solved, a battle in progress, and the worlds left behind — and `start({ game })` restores all of it, so the same intents after a reload meet the same animals, puzzles, leash rolls, wild attacks and doctor puzzles as without one. A reload is never a reroll: not of an encounter (the step count is saved, so the next step is the next one), not of a puzzle (a saved battle comes back mid-puzzle with the same puzzle), not of a throw. A doctor visit is not saved: a reload closes it, keeping what it healed. Enforced by `local-authority.test.ts` § saved games, which cuts one scripted game at ten points (in explore, at the battle menu and mid-puzzle), sends each cut through a save document and JSON, and requires the restored game's next 60 intents to produce the same events as the original's, and checks that the next doctor visit after a restore asks the puzzle the original would have, and that a game saved in another world picks up there and meets the same animals on the same steps; and by the engine's `save.test.ts` § readBattle, which picks up every state of 25 real battles and checks the next step is identical. Design-time (the human asked that a reload never lose progress).

### Nothing runs behind the title, and only a starter starts a game

Until a game is under way — before the first one, and after `leave-game` — `LocalAuthority` takes no intent but `new-game` and emits nothing else: no step, no encounter roll, no doctor visit, no party edit. `new-game` is accepted only then, and only for a choice the engine's `chooseStarter` accepts (a tier-1 species, a nickname that is text) with, when it names the player, a name `checkName` takes (`not-a-name` otherwise). `leave-game` is accepted only while exploring, so neither it nor a new game after it is a way out of a battle or a doctor visit. The autosave writes and sends nothing while the title is up: not before a game starts (`begin` after Continue, or a new game's `welcome`), and nothing after `game-left` but the save it makes of the game being left. Continue starts from the save the page carries on from (`resumable()`), so a tab that walked on while the title was up never has its step count walked back. Enforced by the engine's `starters.test.ts` (every species of the catalog, and malformed choices), `local-authority.test.ts` § the title (walking the reed with no game under way meets nothing; the refusals, mid-puzzle and at the doctor included; a game left and picked up plays on exactly as without leaving), and `autosave.test.ts` § the title. Nor is anyone present behind it: the presence socket opens at a game's `welcome` and closes at `game-left`, and a throwaway game never opens it (`presence-controller.test.ts`). Design-time.

### A player's name is always one `checkName` keeps

Whatever takes a player's name — the title, an authority, a loaded save — asks the engine's `checkName` (`names.ts`): 2 to 16 letters or digits in words joined by single spaces or hyphens, no rude word, tidied (trimmed, single spaces, NFC), and a name it keeps passes again unchanged. The title goes on only with a name it takes and says why not otherwise; `LocalAuthority` checks `new-game`'s name and `choose-name` again and keeps only the tidied name; `restoreGame` checks a stored one again, so a name that is no longer allowed (the rude list grew, a hand-edited save) loads as no name, and the kid is asked for a new one rather than the save being set aside. The server's save backup stores a name as sent, like the rest of the save ([[DEFERRED]] "The server stores whatever save the client sends"); whatever shows a name to other players, or takes it as a username, must ask `checkName` there. Enforced by `names.test.ts` (real names that must pass, rude ones in every spelling that must fail, each reason, and random strings: a kept name is a fixed point within the rules), `save.test.ts` ("a stored name that is not one loads as no name"), `local-authority.test.ts` (refused names start nothing and change nothing) and `title-controller.test.ts` (each refusal keeps the box up with its reason). Design-time: names are seen by other players.

## Saves

### An unreadable save never stops the game, and is never thrown away

`readSave` sorts every stored document into readable, `newer` (a later build wrote it: § below) or `invalid`, and start-up turns an invalid one into a playable game: a new game that leaves the save where it is until the kid has played (a battle ended, the party changed, an accepted party edit, a starter picked on the title), then moves the old text to the first free slot of `animath.save.unreadable` (`.2`, `.3`, …) before the first write, and with no slot free never writes over it. Every other set-aside (`animath.save.replaced`, `animath.save.previous`) works the same way. On the server, an unreadable backup is not replaced until the kid has played either, and the write that replaces it copies it to `save_backups` first. Enforced by `autosave.test.ts` (an unreadable save is untouched by walking, a doctor visit or a refused edit and set aside by a catch; a second one is kept beside the first; with every slot taken nothing is written over), `save.test.ts` § readSave and the upgrade seam, and `players.test.ts` ("a stored save this build cannot read is kept aside"). Design-time; the second-save case from the adversarial review of #19, where the slot was skipped when taken and the save written over.

### A save a newer build wrote is never loaded, written over or set aside

`readSave` calls a document `newer` when its `version` is later than `SAVE_VERSION` or, of the right shape, it names an id, shaped as every catalog id is (`isContentId`), that this build cannot carry on with because none of its catalogs has it (`findUnknownContent`: a species in the party, or in a saved battle its realm, an animal's species or the puzzle's kind), since species only grow (§ "A species that has shipped never leaves the catalog"); a shape no build writes is `invalid`, whatever else it names. An item it does not have is kept as it is and does nothing, so such a save reads. Only ids are seen: a battle a later build's other growth made (an attack added to a species, a realm a species newly goes to, a new phase) is dropped on load as if the kid had run away ([[DEFERRED]]). Such a save waits, untouched, for a build that can read it, in the browser and on the server. A page that finds one at start is behind it (`newer`) and starts nothing, not even the title; one that meets it later (another tab's save, or the server's copy at the first comparison or a backup's `409`) is behind it from then on, so the kid never plays on in a fork of a game a newer build has moved on. Before any write to the key, a page checks that no newer save has landed there unseen, so neither a new game's first write nor setting an unreadable save aside moves one. The server never replaces one (`canReplace`: `409`, whatever the `seq`, nothing kept aside) and stores none it cannot read (`503`: it is the older one, and the client tries again later). A page whose backup the server turns away as a conflict while holding a lower `seq` (a server older than the save it holds, which this page reads) tries again only as it does when the server is out of reach, backing off and then resting until the kid plays, rather than asking again and again. Enforced by `save.test.ts` (newer against invalid, ids of no catalog's shape invalid, an unknown item read; 300 real saves, battles among them, each read as newer with any one of its species, realm or puzzle kind swapped for an unknown one; `canReplace` never over a newer save), `autosave.test.ts` (four kinds of newer save at start, from another tab, landing unseen just before a new game, an unreadable save's set-aside or a walk, and on the server at start and at a backup: never written, moved or sent over; the turned-away backup retried as if out of reach, and taken once the server can), `behind.test.ts`, and `players.test.ts` and `account.test.ts` (`409` whatever the `seq`, nothing kept aside; `503`, nothing stored, no account made). Incident: #89's planning — an older build called a save holding a species it did not know `invalid`, so with two builds live during a deploy, and accounts syncing one save across devices, a stale tab would have set a kid's newer game aside and started a new one in its place. Fixed before any new species shipped.

### A loaded save never strands the player

`restoreGame` gives a game a kid can play from any readable save: a position the player can't be on with what they own (`isPassable` with `gearOf` the saved items: the world generator changed under it, or water without the boat) becomes the spawn tile, an HP above the species' maximum is cut to it (`startBattle` would throw on it at the first encounter), an empty party gets the starter, a party with no animal that can fight on land (only sea animals: no save a kid's game writes holds one, though a `?party=` game, saved nowhere, can start with one) gets the starter behind them, and a battle saved with it is dropped, as it was not fought with the starter, so the grass is never out of reach, and a party with nobody standing rests to full, as a lost battle does. Out on the water with the boat the player stays in it. A saved battle comes back only when `readBattle` accepts it against the restored party and the player is still where it was fought, in the realm it was fought in (a battle saved before battles had one was fought on land), with an animal in front and a wild one that can both fight there. Enforced by `save.test.ts` over 400 random saves of every shape, some with the boat (a tile they may stand on, someone standing, an animal that can fight on land, every HP in range, and a party `startBattle` accepts where one of them stands), by "gives a party of only sea animals the starter too" (red without the rule), by "out on the water with the boat, the player is still in it; without the boat, back on the spawn tile", and by the `readBattle` cases, a battle on the water among them. Design-time; the same promise as "A knock-out never strands the player". Without the boat check, a game that somehow lost its boat would put the kid on a water tile where every step is blocked.

### A new game never loses the game it replaces

New game on the title (a `welcome` with `newGame: true`) is a game of its own: a fresh lineage, numbered on past every save the page has seen. Its first write moves whatever the save key holds — the game the kid left, or another tab's later save of it — to the first free slot of `animath.save.previous` (`.2`, `.3`, … up to 200, since a kid trying the starters puts one away per try) before writing, and with no slot free leaves it where it is and does not save the new game in the browser. A newer build's save is never touched, one that landed there unseen just before the first write included (the page is behind it instead: § "A save a newer build wrote…"), and an unreadable one goes to `animath.save.unreadable` as usual. On the server the new game's backup numbers past the `seq` of the game the kid put away (jumping past it when the server was ahead, never adopting it), so that game lands in `save_backups` like any game a backup replaces. A game the title never showed — the server's, when it was out of reach at start — is not put away: the bigger game wins as it always did, and the new one goes to `animath.save.replaced`. Enforced by `autosave.test.ts` § the title (the old save kept byte for byte, a second new game beside the first, thirty starters tried in turn, full slots never written over, the server ahead, the server out of reach at start, a newer build's save, a tab still playing the old game), with negative controls. Design-time: the human asked that New game never wipe a kid's animals by accident; the offline case, the slots and the walk-back below were found by the adversarial review of #29.

### Every save an older build wrote upgrades to one this build reads, and the upgrade loses nothing

`readSave` chains `SAVE_UPGRADES` from a document's version to `SAVE_VERSION`, and each upgrade is total and lossless: every document valid in its version comes out valid in the next, and the next can be turned back into it exactly. v1 → v2 puts the game in World 1, its home, and keeps everything else as it was: the position, facing and cleared tiles become World 1's, and the party, tokens, items, counts, battle, lineage, `seq` and extras are untouched; what v2 has no place for (a seed other than World 1's, a v1 extra under a name v2 took: `name`, `home`, `world`, `worlds`, and `solved`, which v2 took later) is kept under `v1`, as it was. A v1 document that was unreadable stays unreadable. So an update never sets a kid's game aside as unreadable, and never changes where they stand or what they have. Enforced by `save.test.ts` § the v1 → v2 upgrade (500 random valid v1 documents, extras under v2's names and seeds of every size among them, each upgraded to a valid v2 document it can be rebuilt from; 200 games in the prototype world restored in World 1 with the same position, party, tokens, items, clearings and counts; unreadable ones stay so) and by the kid's own save, run through the upgrade, the old and the new `restoreGame` (identical, field by field) and `LocalAuthority` before the upgrade shipped. Design-time: the first version bump, with one real kid's game 7,400 steps in.

### An older build's save is kept as it was before this build writes over it

Before a page writes its first save over a document an older build wrote (one it read through the upgrade, from the key or another tab's walk), it moves that text, exactly as it was, to the first free slot of `animath.save.upgraded` (`.2`, `.3`, … up to `.20`). With nowhere to keep it (storage full, every slot taken) it writes over it all the same, unlike the other set-asides: the upgrade loses nothing (above), so the new save holds everything the old one did, and holding back would leave the game unsaved in the browser, reload after reload. The server does the same with its copy: the first backup after an update copies the older build's document to `save_backups` before replacing it (`replacesAnotherGame`), and a backup an older build still sends (a page open from before the update) is taken, upgraded. So an upgrade that got something wrong can be undone by hand. Incident: the adversarial review of #92 found the first version holding back the save when the copy would not fit. Enforced by `autosave.test.ts` (the kid's shape of save: kept byte for byte at the first write and only then; a second beside the first; with every slot taken or no room for a copy, the game still saves and a reload carries on from it) and `players.test.ts` (an older build's backup is taken upgraded; the first backup after an update keeps the old document, once). Design-time: the brief for numbered worlds ("Anything that rewrites a save must never lose one").

### A field this build does not know is written back as it was

`validateSave` keeps every top-level field `SaveV2` does not name; the autosave takes those extras (`saveExtras`) from the save it carries on from, and `saveDocument` writes them back unchanged in every save after; the server stores a document as sent. So a later build can add a top-level field to the save without a version bump: an older build still at play (a tab open from before an update, another device of an account) never drops it, though it does not change it either. Unlike an id none of its catalogs has (§ "A save a newer build wrote…"), a field it does not name never makes a save a newer build's. A field that an older build must not carry on with unread takes the bump instead (`SAVE_UPGRADES`): the older build then calls the save newer and leaves it alone. Enforced by `save.test.ts` ("keeps fields it does not know, at the top level and on an animal"; "saveExtras returns only the fields SaveV2 does not name, and saveDocument writes them back") and `autosave.test.ts` ("a field a later build added comes back in every save as it was": through a walk, a catch, a count, the backup and a reload). Checked against `main` before #94's `solved` shipped without a bump: main's build played a save holding `solved: 312` through a battle, travel and every write, and kept it; with the extras dropped, the same check went red.

### A species that has shipped never leaves the catalog

A save naming a species the catalog does not have reads as a newer build's (§ "A save a newer build wrote…"), which no build would ever load again: deleting one from `catalog.ts` would lock every kid holding one out of their game. A species therefore leaves the catalog only with a version bump and a `SAVE_UPGRADES` step that turns it into one still there. Enforced by `save.test.ts` ("still reads a party of any species that has shipped"), which reads a save of every species id that has ever shipped and fails when the catalog grows an id the list lacks. Incident: PR #21's first HUMAN_TODO note said undoing the frog was a deletion from the catalog; the adversarial review showed what that would do to saves (then: every such save set aside for a new game).

### A page never writes over a save it has not seen

Before each write to `localStorage` a page reads the key again and writes only if it holds exactly the text this page last read or wrote. (The one exception is a new game's first write, which moves whatever the key holds aside first: § "A new game never loses the game it replaces".) If another tab saved in between, this page carries on from that save only when `sameProgress` says the other tab merely walked, taking its step and visit counts when they are higher (a count never goes back, so a walk's encounters and doctor puzzles are never keyed twice). That holds with the doctor's card open, whose visit keeps the number and seed it opened with, and in a battle, which is keyed on the higher count from then on, as a reload keys it from the save. Otherwise it is behind and never writes again, locally or to the server, until it reloads. A server answer that finds the key changed carries on from a walk the same way before it decides anything. A `storage` event is judged against the key as it is when the event arrives, not the value the event carried, and a key that has gone is never written back. Two pages writing in the same instant can both pass the check, because a page's view of `localStorage` is brought up to date only between tasks. The page whose save was written over, unseen, keeps it aside (`animath.save.replaced`) when it finds itself behind, or when a `storage` event carries a save of its game numbered no higher than its own, so it is never gone. Enforced by `autosave.test.ts` § two tabs and § two tabs, each with the real authority (a lagging view of the store stands in for the same instant), and `local-authority.test.ts`, each case with a negative control. Incidents: PR #19's Phase 2 — judging the event's value made a tab that had already carried on from another tab's walk decide it was behind, and reload in the middle of a battle. #58 — a tab with the doctor's card open ignored the other tab's walk and wrote the step count back from 16 to 10.

### A page that is behind takes no play

A page that is behind the save (another window played on in its game, another game took its place, the save was removed, or a newer build saved the game) runs no controller and lets no key reach the game, nor text a text box, until it has reloaded into the newest game. A page that may have missed the news (back from the back/forward cache, resumed, or just focused) checks the save again. Behind another window, it reloads at once when it is the window in use, and shows the behind card when it is on screen while another window is in use. Behind for another reason, it reloads as soon as it is on screen (behind a newer build's save, the reload fetches the new version). It reloads itself at most 3 times a minute, and past that it shows the card; the kid's own reloads (Enter, Space, the card's button) always go and never count. Hidden, it waits, and it waits too while a login, a registration or a logout is on its way (a reload would cut it off: a logout the server never hears leaves the next kid on a shared computer in the account), whose own restart catches it up. So nothing a kid does in a page that can no longer save is taken and then thrown away. Enforced by `behind.test.ts` (no page state that is behind maps to `play`; a page reloads by itself only when visible and within the limit; the kid's reloads do not count), `autosave.test.ts` (the cause follows the lineage of the save that put the page behind; `recheck` finds what an event would have) and by the Phase 2 run of the fix for #26 on screen, where two pages play one save. Incident: #26 — after three reloads in a minute, a second window on screen stopped reloading and saving but went on taking play, so a battle won and an animal caught there vanished at the next reload.

### The server keeps the save with the higher `seq`, and never loses a game

A backup lands only with a higher `seq` than the stored save, and never over a save a newer build wrote (`canReplace`); a save it replaces from another lineage, or one it cannot read, is copied to `save_backups` first (`replacesAnotherGame`). The decision runs in one transaction with the player's row locked, so of racing writes exactly one lands. An account's save is written by the same rule (`writeAccountSave`), with the account's row locked and `account_save_backups` for what it replaces, kept newest first within `ACCOUNT_BACKUP_BYTES` per account (always the newest, and at a kid's few kilobytes a game, hundreds of them); its `409` carries the stored save. Enforced by `players.test.ts` § the stale-write guard (409s, backups, eight racing writes of one `seq`, six racing games; removing the row lock fails the second), `account.test.ts` § the account save (the same cases for an account, a New game's replacement kept aside among them, and the budget: thirty small games all kept, megabyte games only the newest two) and `save.test.ts` § which save wins. Design-time.

### An account's save a newer build wrote is never written over; one no build could read is saved past

An account's save follows § "A save a newer build wrote…" wherever the page meets it: at login (`takeAccountGame` never takes one, and never writes over a newer build's copy in the browser), at load and after a `409`, the page is behind it (`newer`), and nothing is pushed over it. An account's game is played on several devices, so at load a page that holds the account's game in the browser asks the server before anything starts (for no longer than start-up waits, the session check included): an old tab never plays on in a fork of a game a newer build saved elsewhere. With the server out of reach it starts as before, and meets the newer save at the first comparison. Behind such a save, a player logged in may log out (the card's Log out, Escape) to play the guest game meanwhile: that writes the pointer and nothing else. A server save that is only invalid (a shape no build writes) is treated as the anonymous backup treats one: left until the kid has played, then saved past, the server keeping it in `account_save_backups` (`replacesAnotherGame`). Enforced by `account-sync.test.ts` (a newer build's save at load, with and without the account's game in the browser, and found while playing: nothing starts or is pushed, both copies unchanged; an invalid one saved past only once the kid has played), `account-api.test.ts` (start-up's one deadline) and `account-session.test.ts` ("never writes over a newer build's copy, nor takes a server save it cannot read"). Design-time: the orchestrator's rule for #89, and #97's classification.

### The guest game and an account's game never share a key, and no move between them writes over a save

The guest game lives under `KEYS`, each account's under `accountKeys(nameKey(name))`, and an `Autosave` writes only the family it was built with. Registering moves the guest game into the account (the account's keys first kept aside, the guest's text put away in `previous`, the anonymous identity kept aside), logging in writes the account's keys only when the server's save is further along (the other kept aside), and logging out removes only the pointer. Enforced by `account-session.test.ts` and `account-sync.test.ts` (an account's game leaves the guest keys byte for byte as they were). Design-time ([[DECISIONS]] § Accounts: "logging in never swaps one game for another behind a kid's back").

### An account's save goes to the server only for the account the page plays

The session cookie names whichever account this browser logged in to last, in any tab, so a cookie that is not this page's account (a logout the server never heard, a login in another tab) would send this game into someone else's. Two guards, one on each side. `accountSaveServer` asks `SessionCheck` first: the save routes hear nothing until `/api/account/me` has named this page's account (by `nameKey`), an answer that names another or nobody stops the pushes (`unknown-player`), and no answer is asked again later. And every request to the save routes names its account (`x-animath-account`), which the server checks against the session as it answers (§ HTTP API, session auth), so a cookie that changes hands between the check and the request cannot carry the save either. The header carries the account's name, which the server keys itself (`nameKey`), so a browser whose Unicode tables differ from the server's still names the right account. A logout names its account the same way and never ends another account's session; a logout still waiting to be sent is held while a login or a registration is on its way (either ends the browser's old session), so a page starting meanwhile cannot end the new one, and is sent again if that page goes away before its answer (`LOGOUT_HOLD_MS`). Logging out leaves the `animath.account` pointer when another tab has pointed it at another account meanwhile. Enforced by `account-api.test.ts` ("sends nothing to the save routes while the session is not this account's", "names its account in each request…"), `account-controller.test.ts` (the waiting logout held aside), `account-session.test.ts` (the hold, and the pointer) and the server's `account.test.ts` § the account a request names. Incident: PR #96's adversarial review. The check stood for the whole page, and a login in another tab while a push was on its way sent the push with the new account's cookie. Design-time.

## Server

### No migration after the anonymous backup shipped drops, alters or empties its tables

`players`, `saves` and `save_backups` hold the anonymous backups, a real kid's game among them, until it moves to production ([[DECISIONS]] § Saves). Every migration after `0002` only adds: no `ALTER`, `DROP`, `TRUNCATE`, `DELETE`, `UPDATE` or `INSERT` on those tables, and no dropping their index. Enforced by `migrations.test.ts`, which reads every later `.sql` file (with a check that the pattern catches each of those statements). Design-time: the accounts brief, written while the kid was playing.

### Every migration file is in the journal, in order

The migrator applies a `.sql` file only when `drizzle/meta/_journal.json` lists it, and only when its `when` is later than the last one applied; anything else is skipped in silence, and the run still says it applied the migrations. So every file has an entry, the entries are in file order with `idx` counting up, and each `when` is later than the one before. Enforced by `migrations.test.ts`. Incident: lawcel, whose setup this project copies, has five early migrations missing from its journal, so a database migrated from scratch there gets a broken schema; [[DEVELOPMENT]] § Migrations has the recipe.

### Only login, register, `/me` (once a month) and a logout that names no account send the session cookie

The save routes and the WebSocket upgrade read the session (`sessionUser`) and never answer with a `Set-Cookie`, neither to slide a session nor to clear a dead one. A request still on its way with the old cookie when the browser logs in to another account answers after the login; had it sent a cookie, clearing the ended session or sliding the old token, the browser would have dropped the new one and the kid would be logged out mid-game. `/me` clears nothing either, and slides a session (sending its cookie again) only once it is `SLIDE_AFTER_DAYS` (30) into its year, because another tab of the same browser can log in while a page is starting. The game's logout names its account (`x-animath-account`) and sends no cookie either: it ends the session, which leaves a cookie that opens nothing, and a cookie it cleared could land after a login another tab made at the same moment. Only a logout that names no account clears the cookie. Enforced by `account.test.ts` ("a save route never sends the cookie…", "an expired session logs nobody in, and nothing clears its cookie but logout", "logout deletes the session…", § the account a request names, and the once-a-month slide), and `accounts-ready.test.ts` for `/ready`, which a page asks before `/me`. Incident: the adversarial review of this feature (#85), before it shipped; the `/me` half was found re-reading its fix, and the named logout's in PR #96's review.

### The server stores no password and no session token, only their hashes

A password is stored as a salted scrypt hash with its parameters (`passwords.ts`), never as sent, and two accounts with one password have different hashes. A session's token lives in the browser's cookie; the server keeps its SHA-256 (`sessions.token_hash`), so a copy of the database logs nobody in. Passwords are compared by hash in constant time, and a name with no account costs a login the same hash (`verifyDecoy`), so the answer's timing does not tell a free name from a taken one. Enforced by `account.test.ts` ("stores a salted scrypt hash, never the password, and only a hash of the session token") and `passwords.test.ts`. Design-time ([[DECISIONS]] § Accounts).

### The game offers an account only while the server says it can keep one

A server can run while accounts cannot work: its database lacks their tables (a development database `pnpm db:migrate` has not reached) or does not answer. There "Save my game" can only end in "We can't reach the game's home", a promise broken to a kid. So `GET /api/account/ready` says whether the database answers and has every table in `ACCOUNT_TABLES`, and the hourly card (`openPrompt`), "Make an account" and "Log in" (`menuItems`), "I have an account" (`title.rows`) and the web app's hint all wait for `account.ready`, which only the server's own `{ ready: true }` sets; no answer is a no. A new way to offer an account follows it too. When the server stops saying yes, the rows go, each menu's cursor staying on its row (`keepingCursors`), a pause menu cursor whose row went landing on Keep playing and never on the row after it ("Log out" follows "Log in", and acts at once), and an hourly card that is up goes, unanswered, until it says yes again; an account card that is up stays with the kid's typing. "Log out" and an account's sync do not wait for it: a logged-in game saves in the browser and sends when it can, as offline. Enforced by `account-controller.test.ts` (the hourly card), `pause-controller.test.ts` and `title-controller.test.ts` (the rows), `account-api.test.ts` (`accountsReady`), `account-ready.test.ts` and the server's `accounts-ready.test.ts`. Incident: PR #96 shipped the hourly card to the human's development server, whose `mathgame` database lacks the accounts' tables: the kid playing there was told after every hour of play to keep his animals safe, and "Save my game" said the game's home could not be reached.

## World

### Every world is playable from its spawn

`spawnPoint(seed)` (`world/spawn.ts`) is a grass tile from which a doctor's tent is at most `SPAWN_DOCTOR_STEPS` (12) steps away on foot, without a tool or the boat (`nearestTent`), and from which at least `SPAWN_ROOM` (1,000) tiles can be reached on foot: the nearest such tile to the origin. A new game starts there, and so does a first visit to a world, so a kid never starts inside water or a tree, walled in, or a long way from the doctor who heals their animals. It searches the tents within 256 tiles of the origin and past that falls back to the nearest grass tile, which no world reaches: every one of the 9,999 was checked when the rule landed (all within 12 steps of a doctor, the spawn at most 74 tiles from the origin). Enforced by `worlds.test.ts`, over 250 world numbers (grass, the doctor, the room, tall grass within 12 tiles) and, tile by tile for a dozen, that no nearer tile would do; `world.test.ts` checks the tile is walkable for 25 seeds. Incident: design-time; before numbered worlds the spawn was the nearest grass tile, and the doctor was 11 to 90 steps from it in the first 41 seeds tried.

### Going to another player never puts the player where they could not stand, or walk on from

`LocalAuthority`'s `go-to` puts the player only on `arrivalSpot`: a tile they could stand on themselves in the world as they left it (ground on foot, and the water too with the boat), never the friend's own tile, from which the tiles they can get to, the way they get about, lead at least `ESCAPE_REACH` (64) tiles from the friend across or down, so a kid who goes to a friend on an island, in a nook of trees or out at sea never lands in a pocket they cannot leave, however roomy it is inside; with no such tile within `ARRIVAL_RADIUS`, the player stays where they are (`go-to-refused`). A first rule asked only for 40 tiles reachable, and put a kid without a boat on a 51-tile island near World 1's spawn for good (the adversarial review of #93). And it is no step: the step count stays, so nothing is rolled and the walk after it meets what it would have met. Enforced by `arrival.test.ts` (against a brute force of the rule, the facing, and six closed pockets of 40 to a few hundred tiles in four worlds) and `local-authority.test.ts` § going to another player (the spot, no step, the refusals, the same encounters after it). Design-time.

### Deep water is water with water all round it, two tiles out, and nothing else is

A tile is `deepwater`, in the `sea` biome, exactly when it is water and every tile within `DEEP_WATER_MARGIN` (2) of it, diagonals included, is water too; every other water tile is `water`, and no land tile is in the sea. So deep water is always at least three steps from land, and a narrow river has none: the shallows are a border a kid crosses before anything that lives out there. A chunk reads the elevation of its tiles and a two-tile margin once, and must give the tiles `tileAtWorld` gives; `travelKindAt`, which `nearestTent` reads to spare the check, is `tileAtWorld`'s kind with deep water read as water. Enforced by `world.test.ts` § deep water, which re-derives the rule from the tiles' kinds over three seeds, and "agrees with tileAtWorld on every tile, deep water at the chunk edges and negative coordinates included". Design-time.

### World 1 is the world every save from before numbered worlds stands in

Every save written before numbered worlds holds a position in one world, the seed of `'prototype'`, and the v1 → v2 upgrade puts every one of them in World 1, so World 1 is that world exactly: `worldSeed(1)` is 821322741, its tiles are the ones those saves stand among, and its spawn is (−2, 6). A change to what `generateChunk` gives for that seed, or to where its spawn is, can put a saved kid in the water or a wall ([[DEFERRED]] "A saved position assumes today's world generator"). Deep water turned some water tiles into deep water and changed nothing else: read back as water in the river biome, every tile within 64 of the spawn tile is what it was before (0 land tiles of 205,861 within 256 changed); the spawn rule of numbered worlds keeps World 1's nearest grass tile, whose doctor is 7 steps away. Enforced by `world.test.ts` ("changed no land"), which pins the world within 64 tiles of spawn by a checksum of every tile, and the same checksum with deep water read back as water, and by `worlds.test.ts` (World 1's seed, its spawn (−2, 6) with the doctor 7 steps away, the nearest grass tile of all). A change to generation or to the spawn rule fails them: check what the change does to saved games (a position on a tile no longer walkable, or walled in) before updating them. Incident: design-time, when deep water became the first change to the world since kids started saving games; World 1 since numbered worlds, when the kid's game was 7,400 steps in.

### Only a tree or a rock is ever cleared, only by its tool, from beside it and facing it

`clearTile` clears a tile only when it is the one next to the player that they face, it is a tree or a rock in the world as they left it, and they own its tool (`CLEARING_TOOL`: the axe, the pickaxe); anything else is a refusal that changes nothing. And whatever the overlay holds (a hand-edited save may name any tile), `clearedTile` turns only a tree or a rock into ground: an edit never touches water, a tent or tall grass, never closes a tile that was walkable, and never makes a tile start a battle. A tent a kid could clear would remove a doctor; water would let them walk off the map before the boat exists. Enforced by `edits.test.ts` (every kind of tile edited round three seeds; walkability only ever gained; `clearTile` from every walkable tile near spawn facing every way checked against `clearableAhead` and the tools owned; each refusal), each red with its check removed. Design-time: the human's son asked for an axe for trees and a pickaxe for rock.

### Travelling keeps every world as the player left it

`travel` (`world/worlds.ts`) remembers the world left exactly as the player leaves it — where they stand, the way they face, the tiles they cleared there — and picks the world reached up exactly as they left it, or at its spawn, facing down, on a first visit. The worlds left behind hold each world once and never the one the player is in, the world left most recently first; past `MAX_WORLDS_KEPT` (100) the one left longest ago is forgotten, never home. Only a spot the player could no longer stand on (the boat gone from a hand-edited save) starts them at that world's spawn, its clearings kept. The party, tokens, items, name and step and visit counts go along untouched, and travel is taken only while exploring, so no battle or doctor visit is ever left behind in another world. Enforced by `worlds.test.ts` (a first visit, a round trip, a spot no longer standable, the cap with home kept, and 300 random journeys over eight worlds checking that each world keeps exactly the clearings made in it and the list keeps its rules) and `local-authority.test.ts` (in a battle or at the doctor it does nothing; going back finds a chopped tree still gone; a game saved in another world picks up there and meets the same animals on the same steps). Design-time: numbered worlds.

### Everything that walks reads the world as the player left it

A tile the player cleared is ground everywhere a tile is judged walkable for them: the authority's `move`, `restoreGame` (a save standing on a stump stays there, not sent to the spawn tile), the knock-out search (`takeToDoctor` → `nearestTent` walks the paths they cut), the lead walking behind (`Follower.place`), the chunks on screen (`ChunkRing`, `editedChunk`) and the title's scenery. One site reading the seeded world instead would disagree with the others: a kid standing in a gap they chopped would be moved to the spawn on reload, or taken past the gap to a tent, or the follower put inside a tree. Enforced by `save.test.ts` ("keep a player standing where they cleared"), `tents.test.ts` ("walks the paths a player chopped", against its own flood fill), `doctor.test.ts` and `local-authority.test.ts` (a battle lost in a spot chopped open), `follower.test.ts` (put on a stump), `render-memory.test.ts` (the chunk comes back without the tree; the title's team gathers on a stump), each red with its site reading the seeded world. Design-time.

### The cleared tiles in a save stay within their budget, and only far chunks grow back

The tiles cleared in every world a save holds share one `EDITS_BUDGET` (24,000 characters). A clear that takes the current world's overlay past it lets whole chunks grow back, farthest from the player first, until it is within it again; and the worlds left behind get what the current world leaves, home's first, then the most recently left, each cut back from the chunks farthest from where the player stood there (`fitWorlds`, after every clear and on restore). Travelling only moves a world's clearings between the current world and the worlds left behind, so it never takes the total past the budget. and `restoreGame` trims a save that holds more the same way (only a hand-edited save or another client can), so no save this build writes is over it; the budget holds the 25 chunks round the player at their fullest (`MAX_ENTRY_LENGTH` each), so no chunk on screen ever grows back and nothing appears under the kid. The text is canonical, so the same tiles are the same save (`sameProgress`), and a client applying `tile-cleared`'s `pos` and `regrown` holds the authority's overlay exactly. Without the budget a keen chopper's save would grow for good: past the 64 KiB a browser lets the backup sent as the page closes carry, and on towards the server's body limit (`SAVE_MAX_BYTES`), where the backup stops. Enforced by `edits.test.ts` (5,000 tiles round home fit and load fast; the worst case trims only the farthest chunks and none within two of the player), `worlds.test.ts` and `save.test.ts` (three worlds' clearings far past the budget come back within it, home's kept whole, the latest left trimmed from far away; random journeys keep every world's clearings as they were), `save.test.ts` (a save half again over the budget comes back within it, the player standing where they cleared), `local-authority.test.ts` (the UI's view equals the authority's while far chunks grow back) and `players.test.ts` (the fullest overlay beside six named animals mid-battle stays under both limits). Design-time; the trim on restore from the adversarial review of #68, which found a hand-edited save kept over the budget until the next clear.

## Encounters

### Every species in the catalog can be met somewhere

For a lead of tier `L`, each biome's encounter table, in the realm of its encounter tile (tall grass is land; deep water, the sea biome's, is water), lists exactly the species of that realm living there at tier `L − 1` or above — plus, inside `WILD_RADIUS`, at the river and in the mountains, every tier-`L` species of the realm that doesn't live there as a visitor when a resident is bigger than tier `L` — all with positive weight, and for every species at least one habitat grows its encounter tile (tall grass, or deep water out at sea) within 8 chunks of spawn. The ground around a tile only re-weighs the species already there, each to a quarter to four times its biome share (§ "The ground changes which animal comes out"), so it never takes a species off a table. Every land species lives in a land biome and every sea animal in the sea and nowhere else, so a tier-1 lead can meet every species of its realm, and every lead every species of the realm no more than one tier below it (the sea animals from the boat, with a lead that swims). A species whose only habitat never grows an encounter tile is unreachable — which the otter was, because the river biome was water and sand only, until the banks got reeds. Enforced by `encounters.test.ts` ("lists the residents from one tier below the lead up…", "every species can be met somewhere by every lead it may challenge", "grows tall grass or deep water in at least one habitat", "lists only animals that live in the realm the tile is in", "lists exactly the biome's species…") over every lead and several seeds, the sea's included, and `habitat.test.ts` ("only the sea animals live only in the water…").

### Fierce animals are rare near spawn and never rarer further out, whoever leads

For every lead tier `L`: inside `SAFE_RADIUS` tiles of the spawn tile, in every biome where anything of tier `L` or above lives, tier `L` holds the majority of the encounter table and tiers `L + 2` and up together hold under 5%; the share of tiers `L + 2` and up is non-decreasing and the share of tier `L` non-increasing in distance; beyond `WILD_RADIUS` every resident of tier `L` or above has an equal share of the biome's table and no visitor remains. It holds by construction on the biome's table (`encounterTable`): from its own tier up, a tier-`L` lead's table is exactly the tier-1 table of a catalog `L − 1` tiers smaller, visitors included, and a tier-1 lead's table is the one [[PRODUCT]] §4 writes out. The mountains, where every resident is bigger than a lead of tier 1 to 3, keep the promise through visitors of the lead's tier (`encounters.ts`); a new biome with no animal of some lead's tier keeps it only if it gets visitors too. A new species or a retuned ratio that breaks any of these fails the suite.

The table on a tile (`encounterTableAt`) keeps the near-spawn part on every tile, in every world, on any ground: a tier's share there is its biome share times its animals' mean ground factor raised to `danger`, which is 0 inside `SAFE_RADIUS`, so the ground only re-divides each tier's share among its animals. Both distance rules also hold on any fixed ground. Only the far endpoint is the biome's: from `WILD_RADIUS` out the ground sorts the equal residents by where they live, as the human asked ([[DECISIONS]] § Gameplay).

Enforced by `encounters.test.ts`: § encounterTable checks the shift and the tier-1 table against its own copy of the tier-1 rule; § encounterTableAt checks both distance rules on every ground in a set; § the start checks every tier's share against the biome's inside the safe radius, for every lead, biome and 729 grounds. Incident: PR #6's tables kept the promise only in biomes with a tier-1 resident, so near spawn the river was all otters and the mountains 83% wolves — and with the prototype seed the tile next to spawn is a river reed, and in 1 world in 7 the nearest tall grass to spawn is on a mountain. PR #64's first cut multiplied every weight by the ground at every distance, which let wolves and bears pass 5% by rocks near home for a lead of tier 2 or 3, in the prototype world too; the adversarial review found it, and the tiers near spawn were given back their biome shares.

### Nothing two or more tiers below the lead comes out, and neither the lead nor the ground changes how often something does

`rollEncounter(rng, site, leadTier)` never returns a species below `leadTier − 1`, where `leadTier` is the tier of the party's first animal that isn't tired (the authority's call). The encounter chance is the roll's first draw and no table or ground feeds into it, so wherever the biome has anything within one tier below the lead or bigger, a step starts a battle for a tier-5 lead exactly when it would for a tier-1 lead, on any ground; where the biome has nothing, the roll is `null` without a draw. A stronger lead therefore meets as many animals as the starter, only bigger ones, except in the biomes where it meets none. Enforced by `encounters.test.ts` (the floor over every lead, biome and distance and in sampled rolls on both sides of both axes; "neither the lead nor the ground changes whether a step starts a battle", seed for seed) and by `packages/client/test/local-authority.test.ts` § the lead, which walks the reed by spawn with a squirrel, a fox (in front, and behind a tired squirrel) and a bear. Design-time: the human's rule, 2026-09-25.

### The ground changes which animal comes out, never whether one does or which ones could

`encounterTableAt` lists exactly the species of the biome's table, in its order. Each species' factor is `HABITAT_BOOST ^ s` (`habitat.ts`), where `s`, from 0 to 1, is how fully its favourite terrain counts within `HABITAT_RADIUS`. Within a tier, the tier's share goes to its animals in proportion to biome weight × factor; a tier's share is its biome share times its animals' mean factor raised to `danger`, normalised. So every animal keeps between a quarter and four times its biome share, none appears and none vanishes. When one tile around turns into a species' favourite terrain (open ground from water, trees or rocks included), that species' share never falls, whoever leads, wherever, at any distance: every species favouring that terrain gains by the same factor `g` and every other species by no more, so every tier's weighed share grows by some `x_u ≤ g`, and the species' share changes by `g · x_t^(danger − 1)` over a weighted mean of the `x_u^danger`, which is at least 1 (`x_t` is its own tier's). A malformed ground (a missing count, `NaN`, a negative) throws on an encounter tile, because a `NaN` weight would fall through the pick's rounding fallback to the last, fiercest animal every time (PR #6's failure with a `NaN` distance). `surroundings(seed, pos)` is a pure function of the world, like a chunk. Enforced by `habitat.test.ts` (the count against a brute-force one on both sides of both axes, the factor against the rule's literals, malformed grounds) and `encounters.test.ts` § encounterTableAt (the same species and the quarter-to-four bound over every lead, biome, distance sample and 729 grounds; the tier-1 table re-derived from [[PRODUCT]] §4's literals on every ground; the shift on every ground; every move of one tile between grounds; the rate and the silence on any ground). Design-time: the human's request, 2026-09-26.

### An encounter can only start on an encounter tile

`rollEncounter` returns `null` for every tile kind that `isEncounterTile` rejects (everything but tall grass and deep water: the shallows too), without drawing from the rng, so a walk's random stream depends only on the steps taken onto encounter tiles. Enforced by `encounters.test.ts` § rollEncounter. Design-time.

## Doctor

### A knock-out never strands the player

`takeToDoctor` either leaves the player where they were or puts them on a walkable tile next to a tent, facing it, that is reachable from where the battle was lost the way the player gets about: on foot, or with the boat (`gear`) over the water too. That holds because `nearestTent` is a breadth-first search over the tiles the player can go to (`isPassable`) from the player, not a straight-line nearest: the tent nearest as the crow flies can be on an island or boxed in by trees, and a kid put there could never walk away, with the position saved. The stand is always walkable ground, never water, even when the way crossed a lake. Out on the water, a battle is lost with animals that can't swim still standing, so `takeToDoctor` is told the realm and asks only that every animal that could fight there is tired. Enforced by `tents.test.ts`, which checks `nearestTent` against its own flood fill over the tent lattice from random starts of every kind and sign, on foot and, from the water and beside it, with the boat, and never lets a boxed-in tent be chosen, and by `doctor.test.ts` § takeToDoctor (out on the water with the boat, over the water to a tent). Design-time.

### A wrong answer at the doctor changes nothing, and healing stops at full

In a doctor visit, an answer `checkAnswer` rejects leaves every animal's HP as it was and puts a different puzzle in place of the one missed; a right one sets exactly the hurt animals of the picked one's species to their `maxHp`, and no other; no step lowers an HP or raises one above `maxHp`. Enforced by `doctor.test.ts` over every species at three HP levels × 25 seeds × every shape of wrong answer (beside a hurt animal of another species, which must stay hurt), "one right answer heals every hurt animal of the patient's species, and no other", and by a check on every step of every visit that each HP change comes with a `healed` event. Design-time; healing by species since the doctor's shop (a team of many of a kind).

### Nothing leaves the team, and no token or tool changes hands, without a right answer to its sum

At the doctor, animals leave the party only on a right answer (`checkAnswer`) to a hand-over's sum, exactly the animals the hand-over named, made better (at `maxHp`) as they go, and never so many that nobody standing stays who can fight on land, where every tent stands (`keep-one`, `keepsATeam`, which the doctor's card asks too: a team of only tired animals meets nothing in the grass, and `restoreGame` rests such a team to full, which would make a reload a free heal; a team of only sea animals could battle nothing on the way back, and `doctor.test.ts` goes red with a standing crab counted); the tokens rise only then, by exactly the hand-over's reward (`homeTokens`). An item joins `items` only on a right answer to a purchase's sum, once (`already-owned`), and the tokens fall only then, by exactly its price, never below 0 (`not-enough-tokens` before the sum is even asked). A wrong answer asks the same sum and changes nothing; `back`, another pick or `leave` puts the sum away and changes nothing. The authority writes what a right answer did back at once (`party-changed`, `belongings-changed`), and the save carries it, so a reload never undoes it and never completes a sum that was not answered. Enforced by `doctor.test.ts`, whose `apply` checks every accepted step of every visit against these rules (the random kid of the replay sweep hands animals over, buys, backs out and misses, and meets every refusal), by its hand-over and buying tests over every item and every shape of wrong answer, and by `local-authority.test.ts` ("animals gone home and tokens given, and an item bought, are written back at once"). The negative controls go red: a purchase on a wrong answer, a balance one token off, and "keep one" counted without asking who is standing. The last was found by the adversarial review of #65. `keep-one` is `canGoHome`, which asks `keepsATeam` of the animals that stay, and the card's picks ask the same functions (and `mustStay`, `kindGoingHome` for a whole kind, which keeps, of the kind's animals not yet picked, the first that can walk on with the kid when no other would), never a copy of the rule, so every pick the card allows is a hand-over the reducer takes: `doctor.test.ts` § "helping a whole kind home" sweeps random teams, sea animals among them, and picks through the reducer, and goes red with the kind picked whole, the wrong animal kept, or a standing sea animal counted as the one who stays. Design-time: the human asked that every token transaction be a sum the kid works out.

### An item is on sale only once what it does is built

The shop sells what `itemsForSale()` lists (the catalog's `available` items), and a `buy` of anything else is refused (`not-for-sale`); only an authority starting a game saved nowhere (`?shop`) widens it. Kids play `main` live: an axe on sale before chopping exists is a kid paying for nothing. Enforced by `doctor.test.ts` ("sells nothing whose effect is not built"), which pins the list on sale, so the change that builds an item's effect is also the one that adds it there, and by `local-authority.test.ts` (a game's shop sells only what is on sale). Design-time.

### A doctor visit is a pure function of `(seed, party, intents)` and keeps the seed out of its state

Like a battle: `applyDoctorIntent(state, intent, seed)` never mutates its input, draws the n-th accepted intent's puzzles from `new Rng(hashInts(seed, n))`, and returns the same state reference with one `rejected` event for an intent that does not fit. The seed is not in `DoctorState`, which goes to the client; a client that knew it could see the next puzzle before asking for it. Enforced by `doctor.test.ts` (frozen input on every step, the replay sweep, and a check of the state's keys). Design-time.

## Party

### The party changes only while exploring

`applyPartyIntent(party, intent, activity)` refuses every intent — choosing a lead, moving, naming — unless `activity` is `explore`, returning the same party with one `rejected { reason: 'not-exploring' }`. A battle, and a doctor visit, each work on their own copy of the party and write it back when they end: an edit made in the meantime would be undone, and a lead chosen mid-battle would name a different animal than the one fighting. The authority says what the player is doing; the engine applies the rule. Enforced by `party.test.ts` ("changes nothing outside explore") and `local-authority.test.ts` (mid-battle edits are refused, and the battle writes back the party it began with). Design-time.

### The party is always in species bundles, and a catch always joins it

Every animal of a species stands with the others of its kind, so the HUD's cards top to bottom are the battle order. `applyPartyIntent` returns a party in bundles from every move it accepts (`select-lead`, `lead-species`, `reorder` only within a bundle, `move-species`; a party that is not in bundles is bundled first), and `rename` changes no one's place. A caught animal joins through `joinParty`: at the end of its kind's bundle, or as a new bundle at the end, however many animals there are. A party from outside is put in bundles on the way in, keeping who leads (`bundled`: when gathering each kind behind its first animal would put a standing animal in front of the lead, as a squirrel caught after a fox that leads behind a tired squirrel, the lead's bundle goes first): `restoreGame` bundles a loaded party (an old save's, whose kinds could be mixed) and a saved battle's party the same way, with the same animal in front, so the battle plays on; the authority bundles `?party=`. Enforced by `party.test.ts` (`bundled` over 400 parties in any order, the same lead before and after, every intent over random parties of up to 150 animals keeping the bundles, `joinParty`'s place over every test party, 300 catches in a row), `save.test.ts` (random saves restore in bundles with the same lead; a save from before bundles, mid-battle, plays on with the same hits) and `local-authority.test.ts` (catches past the old six join their bundle). Design-time: the human asked for one card per species and no cap on the party; the six-animal cap had let a seventh catch go home. The adversarial review of #66 found the first cut of `bundled` changing who led an old save whose first animal was tired.

### The lead is `leadIndex`, wherever it is shown or used

The animal whose card the HUD and the pause menu mark "goes first" (and that an open card tags itself), the one `startBattle` sends out and the one whose tier the authority passes to `rollEncounter` are all `leadIndex(party, realm)` for where the player stands: the first animal in party order with HP above 0 that can fight there (`canFightIn`: out on the water, one that swims), which on land in a party kept in bundles is the first one standing on the first card that has one. The client reads the realm from the player's tile (`game.realm`, the engine's `tileRealm`), as the authority does. (Mid-battle the player decides who is in front, by a switch or by picking who steps in after a knock-out, and the party's order doesn't change: § "Only a `switch` changes the animal in front".) Nothing computes the lead another way, and there is no stored "selected" animal to drift from it: choosing a lead (`select-lead`) moves that animal's bundle to the front and it to the front of its bundle, and is refused for a tired one and for one that can't fight where the player stands (`cannot-fight-here`); choosing a card (`lead-species`) does the same for its first animal standing, and is refused when all of them are tired or the species can't fight there. Enforced by `party.test.ts` (after every accepted `select-lead`, and after every move, `startBattle` sends out `leadIndex`; out on the water, over every party, only a swimmer goes first and it is the one that fights there; `leadIndex` re-derived for both realms) and `local-authority.test.ts` ("a chosen lead is the animal that steps into the next battle", "choosing a lead in explore changes who comes out", "out on the water only an animal that swims goes first"). Design-time; anything new that depends on the lead reads it here.

### A stored nickname is a fixed point of `normalizeNickname`

Every nickname in the authority's party came out of `normalizeNickname`, and cleaning it again changes nothing: 1 to 12 code points of letters (each with at most four marks that belong on it: on a Latin, Greek or Cyrillic letter one of the listed accents; on another letter a mark of its own script, for the listed scripts, or a named generic mark such as an Arabic vowel), digits, `-`, `'`, `.` and single inner spaces, at least one letter or digit, NFKC, no mark on anything but a letter, and nothing default-ignorable (the Hangul fillers are Unicode "letters" that draw as nothing, so a name of them would look blank). Every way a nickname enters the party goes through it — a `rename`, a new game's starter, and the party the authority starts with (`?party=`, or a loaded save, its battle included) — so every screen shows a name as stored and they all agree. One cleaning pass is not enough — about 1 random string in 400 changes on a second pass, because dropping a character can put two Hangul jamo side by side for NFKC to join, and NFKC can turn a letter into an apostrophe look-alike — so the cleaner repeats until a pass changes nothing. Enforced by `party.test.ts` (6,000 strings drawn from hostile Unicode ranges, every rename in random runs of edits, checks that a plainly typed name, in Latin letters or in alphabets that put marks on letters, comes back as typed, and a named list of decorating marks that must all go), `local-authority.test.ts` ("a party it starts with is cleaned like a rename", "cleans a saved nickname the way a rename would, in the party and in a saved battle") and `starters.test.ts` ("cleans the nickname the way a rename does, and drops one with nothing usable left"). Design-time; a one-pass cleaner fails the fuzz. The adversarial reviews of the party-pause PR found, in turn: every mark dropped (misspelling Hindi and Hebrew names); a cap of two that misspelled Burmese "ကျော်" and pointed Hebrew; and a block list of decorations that missed the underline, the overline and a dozen more. The rule is now an allow rule (a mark stays only on a letter it belongs on), and the named lists pin all three.

## Input

### A press acts on one screen, and a new choice never takes a pick from a mash

Each key press goes to exactly one screen, the one up when it goes down, chosen by `main.ts` before any screen acts on it; explore's `Keyboard` hears no key press by itself and starts off, so the key that closes the title, a result card or the doctor's card is never also a step or a word with the doctor. A tap on an overlay button presses only when its pointer went down on the button and comes up on it (or hardly moved) while the same screen is up, each pointer followed on its own (`input/taps.ts`); the number pad and the D-pad press as the finger lands instead, and the browser's click from a pointer presses nothing. Every screen that puts up a choice a kid can't take back takes a pick only after a quiet moment since the choice came up and since the last Enter, Space or number key, counted or not (`input/pick-guard.ts`; which screens, and how long: [[UI_SPEC]] § Battle mode, "A quiet moment"), so a mash at any pace never picks. Enforced by `battle-controller.test.ts`, `doctor-controller.test.ts`, `title-controller.test.ts` and `keyboard.test.ts`, which mash at 2, 4 and 8 presses a second, unevenly and late every fourth (`test/mash.ts`), through the menu, the knock-out list, a won result card, the doctor's list at the tent and after each heal, the confirm, the starters, the name box and Talk; by `keyboard.test.ts` (no key-press listener of its own, nothing taken before explore has the screen); and by `pointer-input.test.ts` (a finger lifted over a button it did not go down on, or on another screen, presses nothing; two fingers tap on their own). Each goes red with the code it replaced. Incidents: #27, a fixed guard after the menu came back, which a long mash outlasted; #37, a mash measured by the gap between two presses (0.3 s), which one slightly slow press in an uneven four-a-second mash broke in 4 turns out of 4, skipping "You won!" too; #38, the explore keyboard queued a talk before `main.ts` routed the Enter to the title's Continue; #39 and #40, the browser's click, which landed on the battle row under a thumb lifted from the D-pad, and never came for a second finger's tap on Talk or Menu.

### A tap presses what its finger touched, or nothing

A pointer key says which list it comes from as well as which row, so two lists a pointer can reach at once never share a key: the pause menu's team and settings are `row:<i>` and the rows beside them (the picked animal's options, or a card's options and animals) `option:<i>` (`input/press.ts`), and the explore HUD's party column names a card by its species and an animal by its id, never by place, and a list under a modal is `inert` (the title's menu under the confirm, whose rows are `row:<i>` too; the shade stops a finger, `inert` a screen reader's click). A button whose key changed while a finger rested on it (a team row another finger moved up) presses nothing when the finger lifts (`input/taps.ts`), which is also why a card carried in a drag is given another key until it is dropped: the drag is never also a tap. The same holds between two presses: the second half of a double click or tap that lands, within `DOUBLE_TAP_MS`, where the first half's button has just moved away from (a re-sort put another there, or the screen changed), on a button with another key, presses nothing. One animal's options, and one card's screen, are a screen apart from another's (`main.ts`), since a tap on the team swaps them in place. Enforced by `pause-controller.test.ts` (every row on the left, beside every animal's options in teams of one to six, and beside every card's screen and its animals' options in teams with cards of several, does what it does on the list and never an option; beside the name box, nothing) and `pointer-input.test.ts` (neither key reads as the other; a row that moved under a resting finger presses nothing; a double click's second half on the row that slid into the first one's place presses nothing, while one on a row that stayed presses it again), each red with the code it replaced; the title's `inert` and the options' screen are checked on screen only (the covered menu out of the accessibility tree; two fingers over CDP). Incidents: #45, the options read every `row:<i>` as their own, so with three animals and the fox's options open, the first team row did Go first for the fox, Language opened New name and Sound did Back; #72, a double click on Pip, second on an open card, put Pip in front, and its second click landed on Rusty, who had slid into Pip's row, so Rusty went first (a card of one animal further down, double-clicked, went to the top and then sent the card that slid down into its place there too).

## Presence

### A socket is in one world at most, and two players see each other or neither

A socket is in the room of the world its last `where` named, or in none, never two: another world moves it, after telling everyone who saw it that it has gone (and it, that they have). Within a room the hub keeps who sees whom both ways at once: two players within `VIEW_RADIUS` see each other, two further apart than `VIEW_KEEP` do not, and every browser draws exactly the players it was told about and no one who left. Enforced by `presence-hub.test.ts`, whose property test walks, moves between worlds, replaces and drops random players and checks after every step that sight is both ways, stays in one world, follows the distances, and that each fake browser's `peer`/`gone` picture equals the hub's own record. Incident: the first version told the others a player had left for another world, but not that player, whose screen kept the old world's players.

### One identity is present once

A second socket of the same guest id or the same account takes the first one's place: the first is told `bye: replaced` and closed, and the others see one player, never two, under the same public id. The page told so stops (`elsewhere`) until it is played in again, so two windows never take the place back and forth. Enforced by `presence-hub.test.ts` and `presence-socket.test.ts` (by guest id and by account) and `presence-connection.test.ts`. Design-time.

### A deploy moves every player to the next server without drawing anyone twice

A server told to stop (SIGTERM, `restart()`) sends every socket `bye: restart` and closes it with `byeCloseCode('restart')` before any close is heard, so no page is told that another left (`gone`), and it takes no new socket. A page that hears either comes straight back (`RESTART_RETRY_MS`), not as a failure, and holds the players on its screen and in its list while it does; public ids are a keyed hash of who each player is with a secret every copy of the server shares (`idSecret`, from `DATABASE_URL`), so the next copy names each player as the last did and the page draws them on where they stood: nobody twice, no poof, no note. With a public id salted afresh per server, as first built, every deploy would have drawn each player twice for three seconds, the old figure fading beside the new. Enforced by `presence-socket.test.ts` (the restart, the same id on two copies sharing the secret), `presence-connection.test.ts` (straight back, by the bye or by the code alone) and `presence-controller.test.ts` (the hop: one figure, no note, no poof). Design-time.

### Nothing off the socket is used before the engine has read it, and nothing a client made up is passed on

Every message, both ways, goes through `parseClientMessage` / `parseServerMessage` (`net/protocol.ts`) before it is used: null for anything that is not exactly a message (every number whole and in its bounds, every text in its length, text only, within `MAX_MESSAGE_BYTES` from a browser and `MAX_SERVER_MESSAGE_BYTES` from the server), and a new object of the known fields, so a field a client added never reaches another client. The server builds every `peer` from what it parsed, and leaves the furthest off a roster too long for a browser to read (`fitRoster`). A browser once read the server with the 4 KiB bound of what it may send, and dropped every roster of a world of about 40 players with long names: the list, Go to and the notes froze. Enforced by `net.test.ts` (every message through JSON and back; any field swapped for junk or missing refused; extra fields dropped), `presence-socket.test.ts` (junk, binary, too big, a flood), `presence-hub.test.ts`, whose fake peers check that everything the hub sends reads back as the same message through the wire's bound, fifty of the longest names among it, and `presence-connection.test.ts` (a roster over 4 KiB read whole). Design-time.

### Presence never stands in the way of play

Nothing in the game waits on the socket, and nothing the socket meets makes it throw: no WebSocket at all, a server that is down, junk from the server, a send on a closed socket. Without a server the game plays exactly as it does alone; a dropped socket is tried again on its own (`BACKOFF_MS`), and the page says only, in the pause menu's list, that it is looking for the others. Enforced by `presence-connection.test.ts` ("never throws") and `presence-controller.test.ts`. Design-time.

## Rendering

### What leaves the screen for good is disposed, so memory stays flat however far the player walks

Taking an object out of a scene frees nothing: three.js keeps a drawn geometry's buffers and vertex arrays, and an `InstancedMesh`'s instance buffers, until that geometry or mesh is `dispose()`d, for as long as the renderer lives. So a chunk that leaves the 5×5 ring is disposed (`ChunkRing` → `disposeChunkGroup`: its ground's and its props' instance buffers, any geometry of its own, its lights), and so is a battle figure when it is replaced or the battle is left (`BattleScene.setFigure`, `end`). A shape many meshes draw is built once and never disposed: the ground box and `PROP_GEOMETRY` in `tiles.ts`, listed in `SHARED_GEOMETRIES` (which `disposeChunkGroup` skips) and drawn by every chunk and the battle backdrops; materials are module constants (`animals.ts` caches the figures' by colour), except where a thing fades alone: another player's trainer and boat copy theirs, and a poof has its own, freed when they go. A chunk therefore owns the instance buffers of its ground and of its props' meshes and nothing else on the GPU, and a new kind of prop is a mesh of a new shared shape, never a geometry per tile. Enforced by `render-memory.test.ts`, which counts live geometries and instanced meshes through their `dispose` events without WebGL: a walk round a square five chunks out never holds anything off screen and ends holding what it started with, a jump or a new world frees the old ring, chunks draw only shared shapes, ten battles in a row leave no figure behind, and the lead walking behind and the title's scenery free every figure they stop showing; by `others.test.ts`, where twenty other players come, walk, jump and go and leave no geometry but the poof's shared puff, nor any of the materials each trainer fades with; and by `battle-controller.test.ts` ("frees both figures once the result card is left"). Incident: #24 — nothing was ever disposed, and every decoration built its own geometry, so 616 steps and 25 battles took live GL buffers from 2,247 to 44,544 and the JS heap from 22 to 45 MB.

## Serving

### A browser keeps only the files a build named after their content, and asks for the page on every visit

The server marks a file `public, max-age=31536000, immutable` only under `/immutable/`, where Vite writes every file it builds under a name that carries its content hash (`build.assetsDir`), so a changed file always has a new name. Everything else, `index.html` included, is `no-cache`: `index.html` names the build's files, so a deploy reaches every kid at their next load, and a file `public/` copies over (the models and textures planned under `/assets/`) keeps its name when it changes. Nothing the server does not find gets the header: a 404 marked `immutable` would be kept for a year. Enforced by `app.test.ts` § the built client (`cacheControl` in `app.ts`, and the header set only on a file `serveStatic` found). Design-time.

### A path the API does not answer is a 404, never the game's page

Every path under `/api` no route answers, and `/ws`, is `404 { error: 'not found' }`; a file missing under `/immutable/` or `/assets/` is a 404 too. Only other paths get `index.html`. During a deploy the old app and the new one answer side by side for a few seconds, and nginx sends a request for a file of the client (under `/immutable/` or `/assets/`) that one of them answers with a 404 to the other one (`nginx/app.conf`): a page of `index.html` with a 200 there would reach the browser as a script, and the game would not start. Enforced by `app.test.ts` § a path nothing answers, § the built client. The nginx half was checked on the local stack with two builds overlapping: with the retry, 80 requests for either build's script and 40 for a public file only one build had all answered 200; without it, 38 of 80 and 22 of 40 were 404s. Incident: the pre-deploy review (2026-09-27) found the server answering unknown `/api/*` paths and `/ws` with `index.html` and a 200.
