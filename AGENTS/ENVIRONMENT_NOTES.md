# Environment notes

Hard-won facts about the local dev environment, the shared resources agents collide on, and how to verify things. None of it is derivable from the code, and all of it has cost at least one session.

**Why this file exists.** Private agent memory is per-agent and per-machine; a second session sees none of it, so the same trap gets rediscovered at full cost. Anything true about *how this repo behaves* belongs here. Private memory is for preferences and conversational state, never for project facts.

This is **record-keeping, not DNA** — it describes what happens to be true right now, so entries change and get deleted as things get fixed. When you fix something listed here, remove the entry in the same PR.

## This machine is shared with the lawcel project

The same Mac runs lawcel's dev stack, often with several worktrees live at once. Two consequences:

- **Postgres.** Lawcel's container owns host port **5432**. Ours (`mathgame-postgres-1`, from the root `docker-compose.yml`) is on **5433**. `DATABASE_URL` in `.env.example` already says so; never "fix" it back to 5432.
- **Ports.** Lawcel dev servers start at Vite's default **5173** and count up. Ours: client **5180**, API **3000**. Before starting a server, `lsof -nP -iTCP:<port> -sTCP:LISTEN` — if something you didn't start is listening, pick another port and pass it explicitly; never kill a listener that isn't yours. Note that Vite binds `localhost` as IPv6 `[::1]` on this machine, so `curl 127.0.0.1:5180` fails while `curl localhost:5180` works; that's normal.
- **The primary clone's dev servers are often already up.** The human (or another session) runs `pnpm dev` from `~/git/mathgame` on 5180 and 3000; `lsof -a -p <pid> -d cwd` shows whose it is. From a worktree, start your own client beside it with `pnpm -F @mathgame/client exec vite --port 5181 --strictPort` (the config pins 5180) and point the screenshot script at it with `--url http://localhost:5181/`. The client saves in the browser, and talks to the API for accounts and presence; the screenshot script blocks the API unless `--api`, and the game plays and saves the same. To exercise accounts or presence, run your own API with your own database, point your Vite at it with `API_PORT` and pass `--api` ([[DEVELOPMENT]] § Running). The primary clone's Vite and API serve the human's tunnel, often with kids on it: never point a test at 5180/3000.
- **A free port can be taken before your server gets it.** Sibling agents start servers all the time: on 2026-09-27 port 5194 was free at `lsof` time and a sibling's Vite held it seconds later, so `vite preview --strictPort` exited, in the background, and a screenshot pointed at 5194 drew the sibling's build of `main`. After starting a server, read its log for "ready" (or `lsof -a -p <pid> -d cwd`) before pointing anything at the port.
- **Every Vite you start proxies `/api` to 3000, the primary clone's API, unless `API_PORT` says otherwise**: the worktree dev server above, and `vite preview` of the built client (`pnpm build` first; much faster than the dev server under load), which inherits the dev server's proxy. Any browser on such a page that is not a throwaway game (`?new`, `?party=`, `?zoo`, `?tokens=`, `?shop`) joins the kids' worlds over presence, and an account made there lands in the human's `mathgame` database. `scripts/screenshot.mjs` blocks the API in the browser unless `--api`; a throwaway Playwright script has to block it itself, with the line in [[DEVELOPMENT]] § Looking at the game. To keep every browser on a Vite away from any API, start it with `API_PORT=3999` (a port nothing listens on; the page plays alone and offers no account), e.g. `API_PORT=3999 pnpm -F @mathgame/client exec vite preview --port <free> --strictPort`, or with your own API's port.

## No `psql` on the PATH

Use `pnpm db:psql -c "<sql>"` (wraps `docker compose exec postgres psql`), or `docker compose exec -T postgres psql -U postgres -d mathgame`.

**From a worktree, pass `-p mathgame`.** Compose names its project after the directory, so inside `../mathgame-worktrees/<branch>/` both `pnpm db:psql` and `pnpm db:up` look for a `<branch>-postgres-1` container and report `service "postgres" is not running` (or, for `db:up`, start a second Postgres that fights for port 5433). The dev database is the container `mathgame-postgres-1`: `docker compose -p mathgame exec -T postgres psql -U postgres -d mathgame -c "<sql>"`. `pnpm db:migrate` is unaffected — it connects through `DATABASE_URL`.

## `git gtr new` may skip the `.env` copy and the `pnpm install` hook

`.gtrconfig` asks gtr to copy `.env` and run `pnpm install` into every new worktree, and for six worktrees on 2026-09-25 and 2026-09-26 (the last `feat/axe-pickaxe`) it did neither: the fresh worktree had no `.env` and no `node_modules`. Without `.env` the server tests fail at startup with `DATABASE_URL is not set` (their vitest config derives the test database URL from it), which looks like a broken merge and isn't. After `git gtr new`, check `ls .env node_modules` in the worktree; if either is missing, `cp ../../mathgame/.env .` and `pnpm install` by hand. Assume it will happen, and check every time.

## Sibling agents share one scratchpad folder

Agents started by one orchestrator run under the same session id (`$CLAUDE_CODE_SESSION_ID`), so their "session-specific" scratchpad is one folder with dozens of files from several branches in it. On 2026-09-25 another branch's `pr-body.md` replaced `feat/encounters-by-lead`'s between two edits, luckily after the PR had been opened from it. Put every scratch file in a subfolder named after your branch (`$SCRATCHPAD/<branch>/pr-body.md`), and never restore a negative control from a generic name like `local.ts.bak` that a sibling may also write.

## `mathgame_test` outlives #100

`mathgame_test` is the database every worktree's server tests shared until #100. A branch that has not merged main since still runs on it, and a run there can still empty the tables under another such branch's run: a lone server failure there, where a test's own rows went missing or a name it registered was already taken, is that, not the branch's change. `pnpm db:prune-tests` lists it as left alone, as it does a test database a sibling named by hand through `TEST_DATABASE_URL` (`mathgame_<branch>_test`, which that sibling drops when it finishes). Drop `mathgame_test` by hand (`docker compose -p mathgame exec -T postgres dropdb -U postgres mathgame_test`) once every worktree has merged main past #100, and delete this entry then.

## The Postgres container's clock runs ~120 ms ahead of the host

Measured with `clock_timestamp()` against `Date.now()`: 116–134 ms, stable across calls. A row whose default is `now()` therefore carries a later timestamp than a `new Date()` computed in Node afterwards, and a test asserting "updated after created" fails. Write timestamps with one clock — the server uses `sql\`now()\`` for `last_seen_at` and `updated_at` — and never compare a Postgres timestamp to a Node one across a gap under a second.

## Looking at the game

The Claude-in-Chrome extension tab shows an error page for `localhost` URLs on this machine (cause not established; both `localhost` and `[::1]` fail while `curl` succeeds). Don't burn time on it: use `scripts/screenshot.mjs` ([[DEVELOPMENT]] § Looking at the game).

**Headless Chrome draws on the GPU here.** Given `--use-angle=metal --enable-gpu` (the script's default on a Mac), it runs WebGL on this Mac's Intel UHD Graphics 630 through ANGLE's Metal backend, the path Chrome itself takes on a Mac: 17 frames a second, against 0.8 for SwiftShader, the software renderer the script used before, measured one after the other at a load average of 20. The frames agree pixel for pixel except at tile edges, where SwiftShader draws faint dark seams the GPU does not (0.06% of the start frame's pixels differ). `--gpu swiftshader` still selects SwiftShader, which logs "GPU stall" performance notes (the script filters them) and fakes shadow softness and anti-aliasing. The next three paragraphs were measured under SwiftShader and not since on the GPU, except that there the 11-key reed walk landed on the reed and met the step-11 animal on the first try at the default `--key-interval`, and a scripted 616-step walk with 25 battles took 7 minutes.

Long walks lose taps under SwiftShader. It can freeze for over a second while new chunks render. Taps pressed during a freeze pile up, and the client keeps only two of them by design, so a 70-key route ends a few tiles short, and short by a different amount each run. For a walk longer than about 20 keys, pass `--key-interval 1300`, add `?debug` to the URL and check the coordinates in the `at:` line the script prints. Short walks are not safe either: on 2026-09-25 the 11-key Left/Right reed walk from [[DEVELOPMENT]] § Playing a battle ended on (-2, 6) with no battle three runs in a row (`--key-interval` 700, then 1300, then 1000 after a leading `wait:4000`), and in another session on (-5, 6), two tiles too far (a 220 ms key hold can take two steps when frames are quick). Putting `shot:<n>` after every key made it land on the reed and meet the Rabbit (the step-11 animal then; a Frog since the ground counts, [[CHEATSHEET]] § Finding a battle fast) on the first try. When a walk's parity matters (alternating onto and off one tile), interleave shots and read the last `at:` line (with `?debug`) before trusting the frame. Under heavy load (several agents' headless Chromes at once, a load average in the 40s) even the same walk ended at `-4, 6` with no battle, at any `--key-interval`. What always landed: a throwaway playwright-core script that presses one key, then polls the `.debug` text (the page opened with `?debug`) until it shows the expected `x, y` (or `.status.opponent` appears) before the next key; it met the step-11 animal every run. To plan a route around water and trees, run a breadth-first search over `tileAtWorld` + `isWalkable` from `spawnPoint` in a throwaway vitest file.

**Game time runs slow when the machine is busy.** Beats, the quiet moment every new choice waits for before it takes a pick (`input/pick-guard.ts`: the battle's menu, lists and result card, the doctor's list, the title's confirm, starters and name box, Talk) and the message line's fade all count frame time, and `main.ts` clamps a frame to 0.1 s. SwiftShader managed 2–3 frames a second alone, but 0.3–1.2 with sibling agents rendering at the same time (load average 50 on 12 cores, 2026-09-25). At 0.5 fps one second of game time takes 20 s: a 1.2 s beat lasts half a minute, the 5 s message fade took 75 s, and fixed `wait:` tokens sized for a quiet machine press keys that are still guarded or mid-beat. For long flows, drive the page from a throwaway Playwright script that waits on what the screen says (a line of text, a class) instead of sleeping. Never press a pick again and again until the screen changes: every Enter, Space or number starts the quiet moment again, so a script pressing faster than the page's game time lets 0.8 s pass never picks at all. Wait for the choice to take it instead (Go! or the result card's button lit: `.pill-button.go:not(.idle)`, `.result .button:not(.idle)`; elsewhere, a second of game time), then press once. `uptime` shows whether the machine is loaded before a run. On the GPU a frame took about 60 ms at a load average of 20, under the 0.1 s clamp, so game time kept pace with the clock.

A frame *inside* a short animation (an iris, a lunge, confetti) is out of reach of any fixed wait under load: one screenshot took longer than the whole 1 s transition on 2026-09-26 (load average 20–34), so the first frame caught was already the battle. Freezing the page's clock (`page.clock`, [[DEVELOPMENT]] § Looking at the game) made every frame land where it was asked, at any load. And don't edit the client's source while a run is going: Vite reloads the page mid-run, and the walk loses its place (on 2026-09-26, before saving, it restarted at (-2, 6) facing down and timed out waiting for a battle that was no longer coming).

Under SwiftShader, two pages of the game in one headless browser crawl. The first keeps drawing through SwiftShader, and a second page in the same browser takes 5 to 20 times as long to start: on 2026-09-25, 50 s against 9 s for the first and 2 s once both were closed, with `?new` (so not the save's doing), and three minutes under load. On the GPU they do not: on 2026-09-26, at a load average of 22, the second page started 4 s after the first, both at full size, and a rename in one showed on the other within a second. Every headless page stays `visible` and `document.hasFocus()` is true in all of them: `bringToFront()` hides nothing, and freezing a page over CDP (`Page.setWebLifecycleState`) did not stop its timers or requests. CDP's `Emulation.setFocusEmulationEnabled(false)` made one page report no focus in a probe, but in a longer run the page reloaded as if focused (Playwright's own focus emulation seems to come back). What was reliable for a window the kid is not using, or a hidden tab: `page.addInitScript` that routes `document.hasFocus` and `document.visibilityState` to flags on `window` (`__focused`, `__hidden`), set with `page.evaluate`, plus a dispatched `visibilitychange`. The game reads both every frame, so the flags behave like a real second window, and a reload starts focused and visible again. What worked for two-tab tests under SwiftShader: shrink the page not in use to 160×100 while the other one works, allow minutes for a page to start, and serve the production build (`pnpm build`, then the server on a spare port) rather than Vite's hundreds of modules. Under the same load a request can be answered and still abort: the page's thread was busy for longer than the request's timeout, so the timer won the race.

For flows longer than one battle (catching, then switching, then a knock-out), such a script can also dispatch every intent it causes to its own Node-side `LocalAuthority` (run it with `packages/server/node_modules/.bin/tsx`, importing `playwright-core` and `local.ts` by absolute path, from a `.mts` file so top-level `await` works): the mirror sees the same steps and intents, so it knows each puzzle's answer and each battle's outcome before the screen shows them. Under the same load the result card's 0.8 s quiet moment lasts several seconds of wall-clock time (it counts frame time, capped at 0.1 s a frame), so wait for its button to light (`.result .button:not(.idle)`) and press Enter once, rather than once after a fixed wait or again and again (which starts the moment over). Such a script passes the page its code as a string (`page.evaluate('…')`, `addInitScript('…')`): tsx wraps every named function in a `__name(…)` helper, and a function handed to the page as a function arrives with the call but not the helper (`ReferenceError: __name is not defined`, 2026-09-26).

**Reduced motion switched mid-run.** `scripts/screenshot.mjs --reduced-motion` sets it for a whole run. To switch it while a page is open, as a kid's system setting might, a throwaway Playwright script sends CDP's `Emulation.setEmulatedMedia` with `features: [{ name: 'prefers-reduced-motion', value: 'reduce' }]`. The CSS follows at once. `motion.reduced` (`/src/motion.ts`) follows through the media query's `change` event, which arrives only with a real frame: with `page.clock` paused it had not flipped 32 ms of fake time later (2026-09-26). Poll `motion.reduced` with short real waits (`page.waitForTimeout(100)`) before stepping the clock on.

**Headless frame rate doesn't measure the scene.** On this Mac a headless page draws 15 to 25 frames a second whatever it draws: on 2026-09-26 main's world at about 600 draw calls a frame and a build of it at about 150 ran at the same rate, and so did a 480×300 window, within a spread of ±5 fps from run to run at a load average of 5. What moved with the scene was the game's own work per frame. To compare two builds, wrap `requestAnimationFrame` in an init script to time each frame callback, and `WebGL2RenderingContext.prototype.drawElements` (and its siblings) to count draw calls, then walk the same route on both, alternating runs: the callback's time and the draw calls are the numbers; the frame rate only says whether the machine was loaded.

**Safe-area insets are Chrome's, not Safari's.** Chrome 153's `Emulation.setSafeAreaInsetsOverride` (the screenshot script's `--safe-area`) sets `env(safe-area-inset-*)` on a page whether or not its viewport says `viewport-fit=cover` (tried both ways on 2026-09-27). Safari without `viewport-fit=cover` boxes the page away from a notch instead, so a Chrome frame with insets cannot show that the viewport lost `viewport-fit=cover`: read `index.html` for that. There is no iOS Simulator on this Mac (no Xcode) to check Safari itself.

## PR images: the repo is private

`raw.githubusercontent.com` answers 404 for this repo's files without a token, so a PR body links its frames the way GitHub's own page serves them to a signed-in viewer: `https://github.com/ulfaslak/mathgame/blob/screenshots/<branch>/<file>.png?raw=true`. The frames go on a side branch `screenshots/<branch>` that holds nothing else; git's plumbing builds it without touching any worktree (`git hash-object -w` each file, `git mktree`, `git commit-tree`, `git push origin <commit>:refs/heads/screenshots/<branch>`). The shell is zsh: with the commit in a variable, write `"${commit}:refs/heads/…"`. In `$commit:refs/…`, zsh reads `:r` as its "drop the extension" modifier, and git refuses the mangled refspec (2026-09-26). To add frames to the branch later, build the new tree from the old one's entries with `git ls-tree --full-tree <commit>`: plain `git ls-tree`, run from a folder of the worktree (`screenshots/<run>/`, where the frames are), lists only that folder's part of the tree, which on this branch is nothing, and the new tip loses every frame the PR already links (2026-09-28, fix/back-beats-rematch).

This Mac has no ImageMagick and Python has no PIL (2026-09-26). To crop a frame, macOS's own `sips --cropToHeightWidth <h> <w> --cropOffset <y> <x> in.png --out out.png` does it. To put before and after side by side, a throwaway Playwright page of `<img src="data:image/png;base64,…">` cells in a CSS grid, with a caption under each, screenshotted with `fullPage: true`, is one sheet. In a zsh command line, quote an argument that holds parentheses or spaces (a caption): an unquoted `(main)` is a glob and fails with "no matches found".

## `page.waitForFunction` does not wait for an async predicate

It takes the returned Promise as a truthy value and resolves at once. On 2026-09-26 a flow that waited for `(await import('/src/state/battle.svelte.ts')).battle.screen === 'party'` went on at once, and every key after it landed on the battle intro. Import the page's modules once with `page.evaluate`, keep them on `window` (`window.__battle = (await import(…)).battle`), and wait with a plain function (`() => window.__battle.screen === 'party'`).

## Two pages' `localStorage` without a server

To try how two pages of one origin share `localStorage` (a race, a `storage` event), no dev server is needed. Give a Playwright context a made-up origin, `ctx.route('http://s2.test/**', (r) => r.fulfill({ status: 200, contentType: 'text/html', body: '<html></html>' }))`, and open two pages on it: each gets real `localStorage`. On 2026-09-26 two such pages, each running a read-compare-write loop in one task, both passed every check, and 4,999 of 10,000 writes were lost. A page's view of the key is brought up to date only between tasks. The unit tests stand in for it with `LaggingView` in `autosave.test.ts`.

## The dev server can keep serving an error after the file is fixed

Twice on 2026-09-26 a worktree's Vite kept showing its red error overlay on every fresh page load for a Svelte file that was valid again. `svelte-check` passed, and so did the tests. The first time, the file had been written twice in quick succession: a scripted edit in two steps, the first leaving a tag unclosed. The second time, a `git merge` left conflict markers in it for a moment. The overlay also blocks every click and tap (Playwright reports `<vite-error-overlay> intercepts pointer events`). When a fresh load shows an overlay for code that type-checks, restart your Vite before debugging anything.

## A script's `import('/src/…')` is a second copy once the dev server has hot-updated

A Playwright script that reads the game's state by importing its modules in the page (`await import('/src/state/title.svelte.ts')`) gets the app's own copy only while Vite has hot-updated nothing under it. Once an edit or a `git merge` touches a file those modules import, however deep, Vite serves the app's imports with a `?t=` timestamp, and the bare path loads a second copy that never changes: a wait on `__title.open` times out with the title on screen (twice on 2026-09-28, feat/birds-in-the-air). Restart your Vite after editing, before driving a page that way.

## A merge that bumps the protocol leaves your running API behind

`PROTOCOL_VERSION` rises with every new species. After a `git merge origin/main` that brings a bump, a client rebuilt from the branch speaks the new version, and an API you started before the merge answers every page's hello with `refresh`. The page then tries again only a minute later, so nobody sees anybody and no match starts, and the two-player driver reports no error: it only prints frames of players alone (2026-09-28, fix/endcard-offline, #144's bump to 7). After such a merge, rebuild and restart your own API along with the client. A page's WebSocket frames (`page.on('websocket')`, `framereceived`) show the `refresh`.

## A negative control's `git revert --abort` refuses after a file was touched

`git revert --no-commit <fix>` then `git revert --abort` is the negative control's recipe, and `--abort` refuses (`Entry '<file>' not uptodate. Cannot merge.`) once any file the revert touched was written in between, even if it was written back exactly as the index has it (2026-09-27: a test file put back from the fix commit to run it against the reverted source). Write it back as the index holds it (`git show :<path> > <path>`), then `git update-index --refresh`, and `--abort` goes through. Better: commit a new test before its fix, so reverting the fix leaves the test in place.

## Docker is colima, and colima sees only the home folder

Docker here runs in colima's Linux VM (context `colima`, x86_64 like the Hetzner server, so an image built here runs there). The VM mounts `/Users/cookie` and nothing else: a bind mount from outside it (`/tmp`, `/private/tmp`, the Claude scratchpad) mounts an empty folder, and nothing says so. On 2026-09-27 a throwaway nginx given its config from the scratchpad found none, served the image's default site, and its 404s passed for a negative control until its `/api/health` came back as an HTML page. Put what a container must read under the home folder: a worktree's gitignored `screenshots/` works. `docker build` is unaffected, since the CLI sends the context to the VM. The Docker CLI here has no buildx, so builds use the classic builder; CI's use BuildKit.

**Testing nginx's config: `nginx` must be the container's command.** The nginx image renders `nginx/nginx.conf.template` only when the command it runs is `nginx`. `docker run … nginx:1.29.8 sh -c 'nginx -t'` tests the image's own default config, and passes whatever the template says (2026-09-27). Run `docker run … nginx:1.29.8 nginx -T`, with the environment and the mount the deploy workflow's nginx check passes, and read the rendered config in its output.

## Production access from this Mac

`~/.ssh/mathgame_deploy` (made 2026-09-27) is the prod server's `deploy` key: Terraform puts its public half on the server, and the offsite backup sync logs in with it. `terraform` is installed from `hashicorp/tap` (1.16.4 on 2026-09-27), and the primary clone's `terraform/` is initialised; there is no `hcloud` CLI. Terraform's state stays in the primary clone's `terraform/`: a worktree is removed after its merge, state and all.

gh's token has the `workflow` scope since 2026-09-27, which a push that adds or changes `.github/workflows/*` needs, and lives in the macOS keychain, no longer in `~/.config/gh/hosts.yml`.

`~/.ssh/known_hosts` knows the server as `animath.xyz` and as `91.98.203.234`. A first `ssh` to a new name for it fails under `-o BatchMode=yes` with "Host key verification failed"; `-o StrictHostKeyChecking=accept-new` adds it. A replaced server has a new host key: `ssh-keygen -R animath.xyz` and `ssh-keygen -R <old ip>` first.

**The deploy workflow's logs print `***` for "deploy".** GitHub hides every secret's value in a run's log, and `VPS_USER` is `deploy`: the word reads `***` wherever it appears ("scripts/***.sh", "No *** — The *** secrets…"). Nothing is wrong; read around it.

**A `curl` loop from here times this Mac's way to Hetzner as much as the server.** On 2026-09-28, with no deploy running, about one new connection to `animath.xyz` in eight took 1 to 3 s, all of it in the TCP connect (a SYN sent again after 1, 2 or 3 s). hetzner.com did the same, github.com did not. During #127's deploy such a loop's slowest answer was 4.2 s, two minutes before the deploy reached the server, while nginx answered every request in 37 ms at most. So the server's side of a deploy is nginx's access log: each line's request time, and the app addresses nginx tried with what each answered ([[DEVELOPMENT]] § What a request meets during a swap). Before blaming the server for a slow `curl`, split it: `-w '%{time_namelookup} %{time_connect} %{time_appconnect} %{time_starttransfer} %{time_total}'`.

## pnpm 12 build-script approval

pnpm 12 refuses to run dependency postinstall scripts unless approved in `pnpm-workspace.yaml` under `allowBuilds` (the older `onlyBuiltDependencies` key is read but not honoured). `esbuild` is approved there. If `pnpm install` ever ends with `ERR_PNPM_IGNORED_BUILDS`, run `pnpm approve-builds <pkg> --yes` — it edits the file for you.

## A negative control on a fix whose commit holds its own test

`git revert --no-commit <fix>` takes the test out along with the fix, so the check still passes and proves nothing. Putting the test back by hand (`git show <fix>:<test> > <test>`) then makes `git revert --abort` refuse ("Entry … not uptodate. Cannot merge."), with the revert half done in the index. On 2026-09-27 (PR #92) the way back that lost nothing: `git show HEAD:<path> > <path>` for each file, `git revert --quit`, `git restore --staged <paths>`. Simpler, with no revert state at all: write the fix's parent source over the file, `git show <fix>^:<src> > <src>`, run the check and watch it fail, then `git show HEAD:<src> > <src>`.

## `scripts/screenshot.mjs` has no `--help`, and without `--url` it opens 5180

The script reads `--url` and defaults it to `http://localhost:5180/`, the primary clone's dev server, and treats any flag it does not know as a value it ignores. On 2026-09-27 (PR #92) `node scripts/screenshot.mjs --help` opened the human's server in a fresh headless browser: the API was blocked, so nothing reached the kids' database, but it is the one port never to point a browser at. Read its header (`sed -n 1,60p scripts/screenshot.mjs`) for the usage, and pass `--url` every time.
