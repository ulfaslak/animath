# Environment notes

Hard-won facts about the local dev environment, the shared resources agents collide on, and how to verify things. None of it is derivable from the code, and all of it has cost at least one session.

**Why this file exists.** Private agent memory is per-agent and per-machine; a second session sees none of it, so the same trap gets rediscovered at full cost. Anything true about *how this repo behaves* belongs here. Private memory is for preferences and conversational state, never for project facts.

This is **record-keeping, not DNA** — it describes what happens to be true right now, so entries change and get deleted as things get fixed. When you fix something listed here, remove the entry in the same PR.

---

## This machine is shared with the lawcel project

The same Mac runs lawcel's dev stack, often with several worktrees live at once. Two consequences:

- **Postgres.** Lawcel's container owns host port **5432**. Ours (`mathgame-postgres-1`, from the root `docker-compose.yml`) is on **5433**. `DATABASE_URL` in `.env.example` already says so; never "fix" it back to 5432.
- **Ports.** Lawcel dev servers start at Vite's default **5173** and count up. Ours: client **5180**, API **3000**. Before starting a server, `lsof -nP -iTCP:<port> -sTCP:LISTEN` — if something you didn't start is listening, pick another port and pass it explicitly; never kill a listener that isn't yours. Note that Vite binds `localhost` as IPv6 `[::1]` on this machine, so `curl 127.0.0.1:5180` fails while `curl localhost:5180` works; that's normal.
- **The primary clone's dev servers are often already up.** The human (or another session) runs `pnpm dev` from `~/git/mathgame` on 5180 and 3000; `lsof -a -p <pid> -d cwd` shows whose it is. From a worktree, start your own client beside it with `pnpm -F @mathgame/client exec vite --port 5181 --strictPort` (the config pins 5180) and point the screenshot script at it with `--url http://localhost:5181/`. The client saves in the browser and backs up to the API in the background; without an API behind your Vite (or with `?new`) the game plays and saves the same, and the screenshot script lists the failed calls instead of failing. To exercise the backup, run your own API with your own database and point your Vite at it with `API_PORT` ([[DEVELOPMENT]] § Running). The primary clone's Vite and API serve the human's tunnel, often with kids on it: never point a test at 5180/3000.
- **Every Vite you start proxies `/api` to 3000, the primary clone's API, unless `API_PORT` says otherwise**: the worktree dev server above, and `vite preview` of the built client (`pnpm build` first; much faster than the dev server under load), which inherits the dev server's proxy. A page served that way backs up to the human's `mathgame` database whenever it is not `?new`. On 2026-09-26 that put five throwaway players in it, with saves naming a species main's server did not know; they were found from a refused backup in the console and deleted by id. When you don't need the backup, start it with `API_PORT=3999` (a port nothing listens on; the game saves locally and the backups fail quietly), e.g. `API_PORT=3999 pnpm -F @mathgame/client exec vite preview --port <free> --strictPort`, or with your own API's port. A throwaway Playwright script can also `page.route('**/api/**', (r) => r.abort())`.

## No `psql` on the PATH

Use `pnpm db:psql -c "<sql>"` (wraps `docker compose exec postgres psql`), or `docker compose exec -T postgres psql -U postgres -d mathgame`.

**From a worktree, pass `-p mathgame`.** Compose names its project after the directory, so inside `../mathgame-worktrees/<branch>/` both `pnpm db:psql` and `pnpm db:up` look for a `<branch>-postgres-1` container and report `service "postgres" is not running` (or, for `db:up`, start a second Postgres that fights for port 5433). The dev database is the container `mathgame-postgres-1`: `docker compose -p mathgame exec -T postgres psql -U postgres -d mathgame -c "<sql>"`. `pnpm db:migrate` is unaffected — it connects through `DATABASE_URL`.

## `git gtr new` may skip the `.env` copy and the `pnpm install` hook

`.gtrconfig` asks gtr to copy `.env` and run `pnpm install` into every new worktree, and on 2026-09-25 it did neither, twice (the second time for `balance/starter-mirror-fights`): the fresh worktree had no `.env` and no `node_modules`. Without `.env` the server tests fail at startup with `DATABASE_URL is not set` (their vitest config derives the test database URL from it), which looks like a broken merge and isn't. After `git gtr new`, check `ls .env node_modules` in the worktree; if either is missing, `cp ../../mathgame/.env .` and `pnpm install` by hand. It happened a third time on the same day, for `feat/encounters-by-lead`, and again on 2026-09-26 for `fix/input-and-battle-ux`: assume it will, and check every time.

## Sibling agents share one scratchpad folder

Agents started by one orchestrator run under the same session id (`$CLAUDE_CODE_SESSION_ID`), so their "session-specific" scratchpad is one folder with dozens of files from several branches in it. On 2026-09-25 another branch's `pr-body.md` replaced `feat/encounters-by-lead`'s between two edits, luckily after the PR had been opened from it. Put every scratch file in a subfolder named after your branch (`$SCRATCHPAD/<branch>/pr-body.md`), and never restore a negative control from a generic name like `local.ts.bak` that a sibling may also write.

## The Postgres container's clock runs ~120 ms ahead of the host

Measured with `clock_timestamp()` against `Date.now()`: 116–134 ms, stable across calls. A row whose default is `now()` therefore carries a later timestamp than a `new Date()` computed in Node afterwards, and a test asserting "updated after created" fails. Write timestamps with one clock — the server uses `sql\`now()\`` for `last_seen_at` and `updated_at` — and never compare a Postgres timestamp to a Node one across a gap under a second.

## Looking at the game

The Claude-in-Chrome extension tab shows an error page for `localhost` URLs on this machine (cause not established; both `localhost` and `[::1]` fail while `curl` succeeds). Don't burn time on it: `node scripts/screenshot.mjs` drives the locally installed Google Chrome headlessly through `playwright-core` (no browser download).

**Headless Chrome draws on the GPU here.** Given `--use-angle=metal --enable-gpu` (the script's default on a Mac since 2026-09-26), it runs WebGL on this Mac's Intel UHD Graphics 630 through ANGLE's Metal backend, the path Chrome itself takes on a Mac: 17 frames a second, against 0.8 for SwiftShader, the software renderer the script used before, measured one after the other at a load average of 20. The frames agree pixel for pixel except at tile edges, where SwiftShader draws faint dark seams the GPU does not (0.06% of the start frame's pixels differ). `--gpu swiftshader` still selects SwiftShader, which logs "GPU stall" performance notes (the script filters them) and fakes shadow softness and anti-aliasing. The next three paragraphs were measured under SwiftShader and not since on the GPU, except that there the 11-key reed walk landed on the reed and met the Rabbit on the first try at the default `--key-interval`, and a scripted 616-step walk with 25 battles took 7 minutes.

Long walks lose taps under SwiftShader. It can freeze for over a second while new chunks render. Taps pressed during a freeze pile up, and the client keeps only two of them by design, so a 70-key route ends a few tiles short, and short by a different amount each run. For a walk longer than about 20 keys, pass `--key-interval 1300`, add `?debug` to the URL and check the coordinates in the `at:` line the script prints. Short walks are not safe either: on 2026-09-25 the 11-key Left/Right reed walk from [[DEVELOPMENT]] § Playing a battle ended on (-2, 6) with no battle three runs in a row (`--key-interval` 700, then 1300, then 1000 after a leading `wait:4000`), and in another session on (-5, 6), two tiles too far (a 220 ms key hold can take two steps when frames are quick). Putting `shot:<n>` after every key made it land on the reed and meet the Rabbit on the first try. Part of it was the script: a key token held its key for 220 ms, longer than a step (0.18 s), so a tap walked two tiles whenever the page drew fast; taps are 100 ms since (`--tap-ms`). When a walk's parity matters (alternating onto and off one tile), interleave shots and read the last `at:` line (with `?debug`) before trusting the frame. Under heavy load (several agents' headless Chromes at once, a load average in the 40s) even the same walk ended at `-4, 6` with no battle, at any `--key-interval`. What always landed: a throwaway playwright-core script that presses one key, then polls the `.debug` text (the page opened with `?debug`) until it shows the expected `x, y` (or `.status.opponent` appears) before the next key; it met the Rabbit on step 11 every run. To plan a route around water and trees, run a breadth-first search over `tileAtWorld` + `isWalkable` from `spawnPoint` in a throwaway vitest file.

**Game time runs slow when the machine is busy.** Beats, the result card's guard, the doctor card's opening guard, the title's confirm, starter and name-box guards and the message line's fade all count frame time, and `main.ts` clamps a frame to 0.1 s. SwiftShader managed 2–3 frames a second alone, but 0.3–1.2 with sibling agents rendering at the same time (load average 50 on 12 cores, 2026-09-25). At 0.5 fps one second of game time takes 20 s: a 1.2 s beat lasts half a minute, the 5 s message fade took 75 s, and fixed `wait:` tokens sized for a quiet machine press keys that are still guarded or mid-beat. For long flows, drive the page from a throwaway Playwright script that waits on what the screen says (a line of text, a class) instead of sleeping, and presses a harmless key again until the screen changes. `uptime` shows whether the machine is loaded before a run. On the GPU a frame took about 60 ms at a load average of 20, under the 0.1 s clamp, so game time kept pace with the clock. Under that load one frame can take longer than Playwright's 30 s screenshot timeout, which the script raised to 3 minutes (2026-09-26, load average 56).

A frame *inside* a short animation (an iris, a lunge, confetti) is out of reach of any fixed wait under load: one screenshot took longer than the whole 1 s transition on 2026-09-26 (load average 20–34), so the first frame caught was already the battle. Freezing the page's clock (`page.clock`, [[DEVELOPMENT]] § Looking at the game) made every frame land where it was asked, at any load. And don't edit the client's source while a run is going: Vite reloads the page mid-run, and the walk loses its place (on 2026-09-26, before saving, it restarted at (-2, 6) facing down and timed out waiting for a battle that was no longer coming).

Under SwiftShader, two pages of the game in one headless browser crawl. The first keeps drawing through SwiftShader, and a second page in the same browser takes 5 to 20 times as long to start: on 2026-09-25, 50 s against 9 s for the first and 2 s once both were closed, with `?new` (so not the save's doing), and three minutes under load. On the GPU they do not: on 2026-09-26, at a load average of 22, the second page started 4 s after the first, both at full size, and a rename in one showed on the other within a second. Every headless page stays `visible` and `document.hasFocus()` is true in all of them: `bringToFront()` hides nothing, and freezing a page over CDP (`Page.setWebLifecycleState`) did not stop its timers or requests. CDP's `Emulation.setFocusEmulationEnabled(false)` made one page report no focus in a probe, but in a longer run the page reloaded as if focused (Playwright's own focus emulation seems to come back). What was reliable for a window the kid is not using, or a hidden tab: `page.addInitScript` that routes `document.hasFocus` and `document.visibilityState` to flags on `window` (`__focused`, `__hidden`), set with `page.evaluate`, plus a dispatched `visibilitychange`. The game reads both every frame, so the flags behave like a real second window, and a reload starts focused and visible again. What worked for two-tab tests under SwiftShader: shrink the page not in use to 160×100 while the other one works, allow minutes for a page to start, and serve the production build (`pnpm build`, then the server on a spare port) rather than Vite's hundreds of modules. Under the same load a request can be answered and still abort: the page's thread was busy for longer than the request's timeout, so the timer won the race. The client's background requests wait 15 s for that reason.

For flows longer than one battle (catching, then switching, then a knock-out), such a script can also dispatch every intent it causes to its own Node-side `LocalAuthority` (run it with `packages/server/node_modules/.bin/tsx`, importing `playwright-core` and `local.ts` by absolute path, from a `.mts` file so top-level `await` works): the mirror sees the same steps and intents, so it knows each puzzle's answer and each battle's outcome before the screen shows them. Under the same load the result card's 0.8 s key guard lasts several seconds of wall-clock time (it counts frame time, capped at 0.1 s a frame), so press Enter again until the HUD is back rather than once after a fixed wait.

## pnpm 12 build-script approval

pnpm 12 refuses to run dependency postinstall scripts unless approved in `pnpm-workspace.yaml` under `allowBuilds` (the older `onlyBuiltDependencies` key is read but not honoured). `esbuild` is approved there. If `pnpm install` ever ends with `ERR_PNPM_IGNORED_BUILDS`, run `pnpm approve-builds <pkg> --yes` — it edits the file for you.
